## 3. 数据契约

建议先采用下面的最小结构；字段名可按现有风格调整，但语义不要扩散。

```ts
// 单元素：一个角色只有一个值
export enum EElement {
    red = 1,
    blue = 2,
    green = 3,
    yellow = 4,
}

// 多种族：按位组合，例如 human | dragon
export enum ERace {
    human = 1,
    animal = 2,
    dragon = 4,
    machine = 8,
    god = 16,
    evil = 32,
    unknown = 64,
}

export interface ICharacterConfig {
    id: string;
    name: string;
    element: EElement;
    race: number;      // ERace 的位组合
    icon?: string;
}

export const TeamCount = 30;
export const TeamSlotCount = 4;

export interface TeamData {
    name: string;
    slots: Array<string | null>;   // 固定 4 个，角色 id 或空
}

export interface TeamSaveData {
    version: 1;
    selectedTeam: number;
    teams: TeamData[];
}
```

补充约定：

- 元素是单值，不做位掩码；筛选时直接比较 `element`。
- 种族是位掩码，筛选时用 `(race & ERace.dragon) !== 0`，不要拆成字符串比较。
- 角色配置加载是异步的（`resources.load`），编队存档是同步的（`localStorage`）；这两条链路不要互相套 `Promise`。
- `CharacterConfigLoader.Load()` 返回可等待的 `Promise<ICharacterConfig[]>`，由 `CharacterController` 在完成后写入 `CharacterModel`；不能只发一个回调后继续当已经加载完成。
- 不要在 `MainWin.onOpen()` 里加载角色配置；由 `AppEntry` 启动流程执行一次，窗口缓存重开不重复读取。

规则：

- 默认 30 队，名称 `编队 1` 到 `编队 30`，每队 4 个空槽，当前编队为 0。
- 同一角色可以重复编入同队不同槽位，也可以出现在不同队伍。
- 槽位用角色 `id`，不要用数组下标或显示名称当身份。
- 编入非法队伍/槽位返回失败，不静默改其他槽。
- 移除只把对应槽位置空。
- 改名允许重名；空名称和长度限制留给 UI 任务决定，数据层不擅自加规则。
- 至少一个非空槽位才允许出战；`CanDeploy` 不检查角色配置是否存在，角色缺失的清理放到 UI/配置接入任务。
- 编辑只改内存；只有 `Save()` 才写盘。关闭或取消界面调用 `Discard()` 丢弃未保存修改。
- 当前编队必须保存并在读取时校验；非法值回退到 0。

## 4. 角色配置

`CharacterConfigLoader` 从 `resources.load('config/characters', JsonAsset)` 读取数组，校验：

- 每一项必须是对象，`id`、`name`、`element` 非空，`race` 必须是非负整数。
- `id` 必须唯一；重复 id 视为配置错误，记录日志并拒绝整份配置（目录为空），测试覆盖该行为。
- 任一项非法时同样拒绝整份配置，避免半份目录继续运行。
- 配置缺失、解析失败或为空时返回空目录并记录日志，不让启动崩溃。
- `CharacterController` 只接已校验的数组，提供 `All()`、`Get(id)`、`Has(id)`；不直接依赖 `resources`。
- `CharacterModel` 保存规范化后的角色目录和 `loaded` 状态，并通过模型事件通知界面。

首批 `characters.json` 用 4 个测试角色，元素使用 `EElement` 数值枚举；不要伪造原作角色名、属性或技能。

## 5. 编队存档

- 主键 `crashfever.teams`，备份键 `crashfever.teams.backup`；与 `crashfever.settings` 完全分离。
- 版本只接受 1；更高版本不覆盖，回退默认并禁止本次会话保存。
- 读取顺序：主键 → 备份 → 默认值；主键损坏时不能让有效备份被覆盖。
- 保存前先校验完整数据；仅把有效的旧主档复制到备份，再写主档。写入失败返回 `false`，保留内存修改和 dirty 状态。
- 读取不会自动写盘。
- 数据结构要求：`teams.length === 30`、每队 `slots.length === 4`、`selectedTeam` 在 0～29；不满足按损坏处理，不用半份数据继续运行。
- `TeamSaveService` 通过注入的 `{ getItem, setItem }` 工作，测试使用内存存储；`TeamStorage` 才接 `sys.localStorage`。

## 6. TeamController 接口

至少提供：

```ts
Initialize(saveService: ITeamSaveService): Promise<void>
GetTeam(index: number): Readonly<TeamData> | null
GetSelectedIndex(): number
Select(index: number): boolean
Assign(teamIndex: number, slotIndex: number, characterId: string | null): boolean
Remove(teamIndex: number, slotIndex: number): boolean
Rename(teamIndex: number, name: string): boolean
CanDeploy(teamIndex: number): boolean
IsDirty(): boolean
Save(): boolean
Discard(): void
```

实现细节可调整，但必须满足：

- 控制器不持有编队数据；当前数据和保存快照都放在 `TeamModel`。
- 控制器不 import `cc`，测试可注入 `ITeamSaveService`。
- 控制器使用绑定模型的事件分发器，不自己创建 `EventDispatcher`。
- `Discard()` 回到最后一次成功读取/保存的状态。
- `Save()` 成功后清除 dirty；失败不清除。
- 初始化只执行一次；重复初始化不能把未保存修改悄悄覆盖。需要重新加载时提供明确的 `Reload()`，不要用隐式副作用。

## 7. 实施顺序

1. `CharacterConfig` + 纯校验 + `CharacterModel` + `CharacterController` + `CharacterConfigLoader`，补 4 个测试角色配置；加载函数使用异步 API，并在完成后填充模型目录。
2. `TeamData`：默认值、深复制、完整校验、版本 1；用工厂函数生成 30 队，不要留稀疏数组。
3. `TeamSaveService`：同步读写、内存键值测试、主备读取、保存失败、高版本保护。
4. `TeamModel` + `TeamController`：模型保存数据与快照；控制器负责编入/移除/改名/切队/空队校验、dirty、Save/Discard。
5. `TeamStorage`：只接 `sys.localStorage`，不写业务规则。
6. `tools/teamtest/`：编译与测试脚本，接入 `package.json` 的 `test:team`。
7. 跑类型检查、lint、测试；整理实现说明后再进入 2.2。

## 8. 关键陷阱

- 不要把编队写进 `SettingsService`，也不要复用设置的主键或备份键。
- 不要每次编入/改名就自动写盘；退出编队界面或进入战斗才统一保存。
- 不要把 `TeamController` 写成依赖 `cc` 的组件；否则纯 Node 测试会退化成引擎测试。
- 不要把角色配置加载放进 `MainWin.onOpen()` 或其他会重复打开的界面；加载集中在 `AppEntry` 启动流程执行一次。
- 不要把种族当单值；它是 `ERace` 位掩码，测试至少包含一个组合种族。
- 不要用队伍下标或角色名称作为角色身份，角色 id 才是稳定键。
- 不要接受缺队、缺槽、越界当前队等半有效存档；要么完整校验通过，要么回退备份/默认。
- 不要在本任务提前做角色属性、技能或战斗数值；元素和种族只用当前枚举/位掩码表达。
- 不要为了数据底座提前改 `MainWin` 或注册 `TeamWin`；界面任务再做。
- 不要把测试写成“为了通过而改断言”；数据规则以本文和 [模块边界](模块边界.md) 为准。

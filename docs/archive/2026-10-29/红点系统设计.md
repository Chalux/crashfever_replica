- `Batch` 同步执行，数据立即生效，仅合并通知；允许嵌套，异常时最外层 flush 已完成修改并透传原异常，不回滚。

## 1. 目标与非目标

目标：

- 红点节点在运行时注册，父子关系显式指定，不靠 ID 前缀猜层级。
- 父节点自动汇总子节点，界面不再各自算总数。
- 计数显示规则统一：0 隐藏、超过上限显示 `99+`、支持只显示圆点。
- 红点脚本挂在常驻节点上，暴露一个字符串 ID，组件自己判断显隐；隐藏只切视觉子节点，不隐藏组件节点本身。
- 界面缓存重开、隐藏再显示时不重复订阅、不丢事件。
- 计数恒为非负整数（所有写入口统一归一），封顶只发生在显示层。
- 核心逻辑不依赖 Cocos，可脱离引擎单测。

非目标（本阶段不做）：

- 不做联网推送、红点优先级、动画和音效。这些后续可以在视图层追加。
- 不把红点树本身写进存档。红点是游戏数据的“视图”，不是数据源。
- 不做可视化红点配置工具；注册代码集中在业务模块里。

## 2. 已确认决策

| 决策点 | 结论 |
| --- | --- |
| 计数上限 | 显示 `99+` |
| 父节点聚合 | 自身计数 + 所有子节点计数求和 |
| 持久化 | 先不做 |
| 注册方式 | 运行时注册节点和父子关系 |
| 视图接入 | 红点脚本挂在常驻节点上，暴露 `redDotId` 字符串，组件自己判断显隐；显隐只切 `Visual` 子节点，组件节点本身不隐藏 |
| 节点标识 | 全局唯一字符串 ID；建议写成 `main/team` 方便阅读，但不解析前缀 |
| 刷新方式 | 变更事件 + 脏 ID 集合，不做每帧轮询 |

## 3. 数据模型

### 3.1 显式注册树

父子关系由注册时显式指定：

```ts
RedDot.Register('main', null);              // 根节点
RedDot.Register('main/team', 'main');
RedDot.Register('main/stage', 'main');
RedDot.Register('main/stage/1001', 'main/stage');
```

```
main
├─ main/team
└─ main/stage
   └─ main/stage/1001
```

规则：

- ID 是不透明字符串，全局唯一；`main/team` 只是命名习惯，`/` 没有解析含义。
- ID 必须满足 `isValidId`：非空字符串、无首尾空格（不做静默 trim，否则注册与查询会对不上）。建议动态 ID 先做字符过滤（见 §10 第 18 条）。
- 根节点的父 ID 传 `null`（或省略）。
- 父节点必须先注册。父节点不存在时注册失败并记错误日志，不做隐式创建。
- `parentId` 不得等于自身（自环）；由于父节点必须先存在，多节点互相成环在注册阶段不可能成立。
- 同一 ID 重复注册：父 ID 相同视为幂等（**忽略新的 `initialCount`，记 `Log.warn`**，避免「以为重设成功但数字静默丢失」）；父 ID 不同视为错误，记 `Log.error` 并保留第一次的父子关系。
- 允许多个根节点，例如 `main`、`battle`、`shop` 各自成树。
- `Unregister(id)` 会移除该节点及其整棵子树，父节点计数随之重算；被移除的节点与全部子孙都进入脏集，对应的视图据此隐藏。
- 动态列表项（关卡、角色、邮件）在创建时注册，在数据项销毁时注销；不要只 `Clear`，否则注册表会越积越大。
- 列表全量重建时，先 `Unregister` 旧 ID（或旧父节点整棵子树）再注册新的；不要「只注册新的、旧的留着」，否则注册表与视图都会残留。

### 3.2 三层职责

| 层 | 谁负责 | 典型调用 |
| --- | --- | --- |
| 注册树 | 业务模块启动、列表项创建 | `RedDot.Register(id, parentId)` |
| 计数 | 业务数据变化 | `RedDot.Set/Add/Clear` |
| 视图 | 红点组件 | 读取 `RedDot.Get(id)` 并决定显隐 |

视图组件不参与树注册：组件只知道自己的 ID，不知道父 ID，让组件去注册会破坏父子关系。父 ID 由业务代码明确指定。

### 3.3 两种计数语义，不要混用

| 语义 | 例子 | 数据来源 | 清零时机 | 是否需要持久化 |
| --- | --- | --- | --- | --- |
| 待处理 / 可领取 | 未领奖励 3 个 | 游戏数据 | 领取后数据自然减少 | 不需要，启动时重算 |
| 未读 / 新内容 | 新角色 2 个 | 业务的“已读”标记 | 用户看到后标记已读 | 需要业务保存已读标记 |

同一个红点只能选一种语义。把“未读”和“可领取”加在同一个数字里，会导致用户看不懂为什么数字不减少。

树级约束：**同一棵子树的路由必须使用同一种计数语义**，父节点 `total` 只汇总同语义子项。不同语义的入口（例如「可领取」的编队与「未读」的关卡）不要挂在同一个父节点下；如果因为界面需要必须共用一个父入口，则父入口只显示圆点（任意子项 > 0 即亮），**不显示数字**，数字只在叶子语义内显示。§3.4 的聚合示例只演示数值，不代表可以跨语义聚合。

### 3.4 聚合公式

```
total(id) = own(id) + Σ total(child of id)
```

示例：

| ID | 自身 | 聚合结果 | 显示 |
| --- | ---: | ---: | --- |
| `main/team` | 2 | 2 | `2` |
| `main/stage/1001` | 100 | 100 | `99+` |
| `main/stage/1002` | 20 | 20 | `20` |
| `main/stage` | 0 | 120 | `99+` |
| `main` | 0 | 122 | `99+` |

计数是真实值，封顶只发生在显示层。以后要改成“父节点取最大值”也只改聚合函数，不动界面。表中 `main/stage/1002` 是动态注册的关卡节点（见 §8 动态列表示例），不是静态注册项。所有写入口（`Set` / `Add` / `Register(initialCount)`）都按 §5.1 的归一规则落库，因此 `total` 恒为非负整数。

### 3.5 `Clear`、`ClearTree`、`Unregister` 的区别

| API | 影响 | 用途 |
| --- | --- | --- |
| `Clear(id)` | 只把自身计数置 0 | 用户已读、已领取 |
| `ClearTree(id)` | 自身和所有子孙计数置 0（自底向上重算整棵子树） | 整个模块重置 |
| `Unregister(id)` | 从注册表移除自身和整棵子树 | 列表项销毁、模块卸载 |

`Clear` / `ClearTree` 对未注册 ID 静默忽略（见 §5.1 契约表）。

建议：进入页面时不要无脑 `ClearTree`。父页面只清自己的“新内容”标记，子项在用户真正看到或领取时再清；否则用户刚点进列表，所有子项红点就一起消失了。

### 3.6 生命周期规则

- 每次启动都要重新注册树；注册不是存档内容。
- `Register` 必须在 `Set` 之前；对未注册 ID 调 `Set` / `Add` 会记错误并忽略。
- `Initialize()` 幂等：重复调用只记警告并返回，**不重建 store、不清监听**（见 §5.2）。
- `ResetCounts()` 只把所有计数归零，保留注册树；等价于对所有根执行 `ClearTree` 并只发一次事件，用于导入存档后重算。
- `Dispose()` 清空注册树和 store 的监听；门面到 dispatcher 的转发监听会被摘掉，但 **dispatcher 本身不 `clear()`**（保持对象身份稳定，见 §5.2）。用于应用退出或整体重启。`Dispose` 之后要再调用 `Initialize()` 才能继续使用，且此期间到达的退订调用必须是**无害 no-op**。
- 动态列表项的生命周期：数据项创建 → `Register`（可带初始计数）→ 挂到激活节点 → 设置组件 `redDotId`；数据项移除 → `Unregister`。对象池回收但数据项还在时不要注销。视图侧优先用 §5.4 的常驻节点方案，此时「挂树 / 设 id」的先后不再敏感。

## 5. API 设计

### 5.1 核心 Store

```ts
export interface RedDotChange {
    /** 发生变化的节点、新注册节点、被移除的节点及其子孙，以及 total 因此变化的全部祖先。 */
    readonly ids: ReadonlySet<string>;
}

export interface RedDotNodeInfo {
    readonly id: string;
    readonly parentId: string | null;
    readonly own: number;
    readonly total: number;
}

export type RedDotListener = (change: RedDotChange) => void;

/**
 * 以下为签名示意（方法体在实现里补全）。
 * 约定：所有写入口的计数都先过 normalizeCount：
 *   normalizeCount(v) = Number.isFinite(v) ? Math.max(0, Math.floor(v)) : 0
 */
export class RedDotStore {
    /**
     * 注册节点。父节点必须已注册且在注册表中，parentId 不得等于自身。
     * 根节点 parentId 传 null 或省略。
     * initialCount 只在首次注册时生效，默认 0，按 normalizeCount 归一。
     * 同 ID 同父重复注册是 no-op（忽略新的 initialCount，记 Log.warn）；
     * 同 ID 异父注册失败（记 Log.error，保留第一次的父子关系）。
     */
    register(id: string, parentId?: string | null, initialCount?: number): boolean;

    /** 注销节点及其整棵子树；未知 ID 静默忽略。被移除的节点与全部子孙都进入脏集。 */
    unregister(id: string): void;

    /** 未注册返回 false。 */
    isRegistered(id: string): boolean;

    /** 覆盖自身计数；负数按 0、小数向下取整、NaN/Infinity 按 0。未注册 ID 记 Log.error 并忽略。 */
    set(id: string, count: number): void;

    /** 在自身计数上增减；delta 先归一，结果再 clamp 到 0 以上并向下取整。未注册 ID 记 Log.error 并忽略。 */
    add(id: string, delta: number): void;

    /** 只清自身；未注册 ID 静默忽略。 */
    clear(id: string): void;

    /** 清自身和所有子孙（自底向上重算整棵子树）；未注册 ID 静默忽略。 */
    clearTree(id: string): void;

    /** 聚合值：自身 + 全部子孙；未注册 ID 返回 0。 */
    get(id: string): number;

    /** 自身直接计数，不含子孙；未注册 ID 返回 0。 */
    getOwn(id: string): number;

    /** get(id) > 0；未注册 ID 返回 false。 */
    has(id: string): boolean;

    /** 合并多次注册/写入，只发一次变更事件；支持嵌套；用 try/finally 保证异常时深度回退。 */
    batch(fn: () => void): void;

    /** 注册变更监听，返回退订函数；重复调用退订函数是 no-op。 */
    onChanged(listener: RedDotListener): () => void;

    /** 调试/测试用快照；必须满足 total === own + Σ children.total。 */
    snapshot(): readonly RedDotNodeInfo[];

    /** 所有计数归零，保留注册树；等价于对所有根执行 clearTree，并作为一个隐式 batch 只发一次事件。 */
    resetCounts(): void;

    /** 清空注册树、计数和监听；之后需要重新 Initialize 才能使用。 */
    dispose(): void;
}
```

实现要点：

- 内部维护 `nodes`、`children`、`total` 三张表。普通写入后沿父链向上重算，复杂度是 `O(深度 × 子节点数)`。
- **子树重算（v3 补）**：`clearTree` / `resetCounts` 必须**自底向上重算被清零子树的每一个节点的 `total`**（可逐个节点按写入处理，也可一次后序遍历），再沿父链向上重算祖先；不允许只重算祖先。否则 `get(子节点)` 会读到旧缓存，视图收到事件后仍显示旧数字。
- **脏集统一规则（v3 补）**：
  `脏集 = { total 发生变化的节点 } ∪ { 新注册节点 } ∪ { 被移除的节点及其全部子孙 }`；
  事件仅在脏集非空时发送（batch 内合并）。注册/注销即使没有 `total` 变化也要通知（例如 `initialCount = 0` 的新节点、计数全 0 被注销的子树），否则视图不会刷新。
- **批量与净零变化**：批量期间只累积脏 ID，最外层 `batch` 结束时统一发送。若要以 batch 起点为基线、在 flush 时剔除「净变化为 0」的节点，则必须在这一步复核；不做复核就只能承诺「单次写入不广播」，不要承诺「batch 内总数不变一定不广播」。
- **重复写入合并**：写入前记录受影响节点（当前节点 + 祖先）的旧聚合值，写入后比较；单次写入聚合值没变就不进脏集。
- **监听器重入（v3 补）**：监听器原则上只读。允许监听器内再写红点，但新产生的脏 ID 进入下一轮（`nextRound`），当前一轮发完后再发，**每轮最多广播一次**；监听器异常用 `try/finally` 隔离并保证 `_emitting` 一定复位；同一监听器连续触发 3 轮以上记 `Log.error`（防重入死循环）。禁止监听器里同步递归广播。
- **载荷所有权**：每次广播传入一份新的 `Set` 快照（实现不得复用可变 Set），否则监听器可能互相污染或拿到下一轮内容。
- **未注册 / 非法输入契约**：

  | 操作 | 未注册 ID | 非法 ID（空串、首尾空格、非 string） |
  | --- | --- | --- |
  | `get` / `getOwn` | 返回 `0` | 返回 `0` |
  | `has` / `isRegistered` | 返回 `false` | 返回 `false` |
  | `set` / `add` | `Log.error` + 忽略 | `Log.error` + 忽略 |
  | `clear` / `clearTree` / `unregister` | 静默忽略 | 静默忽略 |

  视图可以假定「未注册 ID 的 `Get` 永远安全且返回 0」。
- **计数归一（v3 补）**：`set`、`add` 的结果、`register(initialCount)` 统一用 `normalizeCount`；`add` 的 delta 先归一（`NaN` / `Infinity` 视为 0）再加、再 clamp、再向下取整，保证「结果恒为 0 以上的整数」对 `NaN` 也成立。
- **`batch` 异常语义（v3 补）**：必须用 `try/finally` 保证 `batchDepth` 回退；`fn` 抛异常时，先按最外层规则 flush 已累积的脏 ID（或明确丢弃并 `Log.error`），再把原异常向上抛；嵌套 batch 逐层回退。否则一次异常会让事件泵永久静默。
- **ID 校验**：`isValidId(id) = typeof id === 'string' && id.length > 0 && id === id.trim()`；不要静默 `trim`（否则注册与查询对不上）。
- **错误处理**：非法 ID、父节点不存在、异父重复注册都记 `Log.error` 并拒绝，不抛异常，避免一个配置错误拖垮启动；幂等调用（同父重复注册、未知 `unregister`）记 `Log.warn` 或静默，不用 error，避免启动期刷屏。
- 单个监听抛异常只记日志，不影响其他监听，和现有 `EventDispatcher` 的行为一致。

### 5.2 静态门面

```ts
export class RedDot {
    static Initialize(): void;
    static Dispose(): void;

    static Register(id: string, parentId?: string | null, initialCount?: number): boolean;
    static Unregister(id: string): void;
    static IsRegistered(id: string): boolean;

    static Set(id: string, count: number): void;
    static Add(id: string, delta: number): void;
    static Clear(id: string): void;
    static ClearTree(id: string): void;

    static Get(id: string): number;
    static GetOwn(id: string): number;
    static Has(id: string): boolean;
    static Batch(fn: () => void): void;

    /** 返回退订函数。 */
    static OnChanged(handler: (change: RedDotChange) => void): () => void;

    static ResetCounts(): void;

    /** 调试用：与 Store.snapshot 同义，供控制台/验收断言。 */
    static Snapshot(): readonly RedDotNodeInfo[];

```

门面内部持有一个 `RedDotStore` 和一个**模块级单例** `EventDispatcher`，对外用 `EventKey` 广播：

```ts
import { EventKey } from '../Event/EventDispatcher';

export const RedDotEvent = {
    changed: new EventKey<RedDotChange>('reddot.changed'),
};
```

门面生命周期契约（v3 新增，必须按此实现）：

- **dispatcher 身份稳定**：`EventDispatcher` 是模块级单例，**永不重建**；`Initialize` / `Dispose` 都不创建新的 dispatcher。
- **`Initialize()` 幂等**：已初始化时记 `Log.warn` 后直接返回，不重建 store、不清监听。重复调用不会留下旧监听，也不会丢已订阅的视图。
- **懒初始化**：忘记调用 `Initialize` 时，首次访问任一 API 自动初始化（编辑器单独预览红点 prefab 也能工作），且与显式 `Initialize` 使用同一个 dispatcher 单例。
- **`Dispose()`**：只 `store.dispose()` 并摘掉门面自己到 dispatcher 的转发监听，**不调用 `dispatcher.clear()`**；之后可再次 `Initialize`，已订阅的视图不会因为 dispatcher 被清而永久失聪。`Dispose` 之后到达的退订调用允许多次调用，必须是 no-op。
- 所有 API 在未初始化时按懒初始化处理，不抛异常；`Initialize` / `Dispose` 本身也不抛异常。

`OnChanged` 的实现要点（`EventDispatcher.on` 不返回退订函数）：

```ts
// 门面内部
static OnChanged(handler: (change: RedDotChange) => void): () => void {
    const wrapped = (change: RedDotChange): void => handler(change);
    dispatcher.on(RedDotEvent.changed, wrapped);
    return () => dispatcher.off(RedDotEvent.changed, wrapped);
}
```

同一 handler 不要重复订阅（`off` 按 handler 身份只删第一个）；需要按宿主批量退订时用 `EventDispatcher.offCaller(caller)`，但门面签名不暴露 caller，红点事件统一走返回退订函数。

接线位置：`Initialize` 在 `AppEntry.start` 里、`SettingsService.Initialize()` 之后、`registerAppRedDots()` **之前**、`UIManager.init` 之前调用（`AppEntry.ts:31` 之后、`:35-53` 之前）；`Dispose` 放在 `AppEntry.onDestroy` 的 `UIManager.dispose()` 之后。两处都必须幂等、不抛异常。

### 5.3 计数归一与格式化

```ts
/** 所有写入口共用的归一规则：非有限 → 0，负数 → 0，小数向下取整。 */
export function normalizeCount(value: number): number {
    return Number.isFinite(value) ? Math.max(0, Math.floor(value)) : 0;
}

export function formatRedDotCount(count: number, maxCount = 99): string {
    const safeMax = Number.isFinite(maxCount) && maxCount >= 1 ? Math.floor(maxCount) : 99;
    const safe = normalizeCount(count);
    return safe > safeMax ? `${safeMax}+` : String(safe);
}
```

放在独立文件，Store 的写入口、视图和单测共用，避免“99+/归一”规则散落在各处。

契约：

- `maxCount` 非有限或 `< 1` 时按 99 处理。
- `count` 非有限按 0、负数按 0、小数向下取整（与 `normalizeCount` 一致）。
- **`count` 恰等于 `maxCount` 时显示原数字**（`99` → `"99"`），只有 `count > maxCount` 才显示 `${maxCount}+`（`100` → `"99+"`）。
- `count = 0` 返回 `"0"`，**不返回空串**；调用方（视图）负责在计数为 0 时隐藏，不要把 `"0"` 显示出来。
- 计数是真实值，Store 不封顶；显示层封顶只发生在 `formatRedDotCount`。

### 5.4 视图组件

组件挂在**常驻节点**上，暴露 `redDotId`，自己判断显隐；**组件节点本身永远不隐藏**，显隐只切 `Visual` 子节点。这是 v3 的主方案，理由是它同时解决三个问题：订阅时机可控、避免在 `onEnable` 里改自身 `active` 的未验证行为、`Widget` 对齐始终有效。

```ts
import { _decorator, Component, Label, Node } from 'cc';
import { BindingScope } from '../UI/BindingScope';
import { RedDot } from './RedDot';
import { formatRedDotCount } from './RedDotFormat';

const { ccclass, property } = _decorator;

@ccclass('RedDotBadge')
export class RedDotBadge extends Component {
    @property({ tooltip: '红点 ID，必须是已注册节点；建议用 AppRedDotId 常量' })
    private _redDotId = '';

    @property({ type: Node, tooltip: '视觉根节点；只切它的 active，组件节点保持激活' })
    private _visual: Node | null = null;

    @property({ type: Label, tooltip: '计数文本；留空则只显示圆点' })
    private _countLabel: Label | null = null;

    @property({ tooltip: '只显示圆点，不显示数字' })
    private _dotOnly = false;

    @property({ tooltip: '超过该值显示 N+，默认 99；非法值按 99' })
    private _maxCount = 99;

    private readonly _binder = new BindingScope();

    public get redDotId(): string {
        return this._redDotId;
    }

    public set redDotId(value: string) {
        if (this._redDotId === value) return;
        this._redDotId = value;
        this._refresh();
    }

    /** 当前订阅数，仅供开发期验收：缓存重开前后都应为 1。 */
    public get BinderCount(): number {
        return this._binder.count;
    }

    protected onLoad(): void {
        // 订阅只在 onLoad 登记一次；组件节点常驻，不随显隐反复订阅。
        this._binder.add(
            RedDot.OnChanged((change) => {
                if (change.ids.has(this._redDotId)) this._refresh();
            }),
        );
        // 防御：redDotId 可能在首次激活前就被赋值，这里先按当前状态刷一次。
        this._refresh();
    }

    protected onEnable(): void {
        // 缓存重开 / 窗口重新显示时从当前状态补一次快照；不在这里重新订阅。
        this._refresh();
    }

    protected onDestroy(): void {
        this._binder.unbindAll();
    }

    private _refresh(): void {
        const id = this._redDotId;
        if (!id) {
            this._setVisible(false);
            return;
        }

        const total = RedDot.Get(id);
        const visible = total > 0;
        this._setVisible(visible);
        if (!visible) return;

        if (this._countLabel) {
            this._countLabel.node.active = !this._dotOnly;
            if (!this._dotOnly) {
                this._countLabel.string = formatRedDotCount(total, this._maxCount);
            }
        }
    }

    private _setVisible(visible: boolean): void {
        const target = this._visual ?? this.node;
        if (target.active !== visible) target.active = visible;
    }
}
```

`_visual` 留空时退化为「切组件节点自身」的单节点方案，此时必须额外满足两条守卫（否则会永久失聪）：

- `redDotId` 的 setter 在 `onLoad` 之前只记录目标状态、不改 `node.active`；
- 列表项必须**先挂到激活节点、再设 `redDotId`**；`onLoad` 里再补一次 `_refresh()`。

为什么不用 `BaseCmp`、也不继承 `BaseUI`（三类订阅生命周期，必须分清）：

| 挂载方式 | 订阅生命周期 | 对 badge 的影响 |
| --- | --- | --- |
| `BaseWin` / `BaseMask`（窗口根） | 框架每次 `Open` 前先 `invokeResetBindings()` 再 `invokeInitEvent()`；`onLoad` 只执行一次 | 订阅必须写在 `initEvent()`；写在 `onLoad` 会被清掉且永不重登记 → 禁用 |
| `BaseCmp`（嵌入组件） | 自身 `onEnable → initEvent`、`onDisable → binder.unbindAll()`；框架不 reset 子组件 | 任何一次 `onDisable`（组件节点被隐藏、窗口 `hideBelow`、缓存关闭摘树）都会退订且不再重登记 → 禁用 |
| 普通 `Component`（本方案） | 私有 `BindingScope` 不归框架管；`onLoad` 订阅一次、`onDestroy` 退订 | **必须自己保证 `onDestroy` 退订**，不能依赖框架兜底；这是对 `Frame/UI/README.md` 订阅纪律的受控例外 |

其他约定：

- 组件节点在 prefab 里必须默认 `active = true`，让 `onLoad` 至少执行一次；运行时**不要**再把组件节点设为 `inactive`（隐藏只切 `_visual`）。
- `_redDotId` 是序列化字段，prefab/编辑器改值**不会走 setter**，要等一次 `onEnable` 或事件才生效；运行时改 ID 请走 `redDotId` setter。
- 事件在节点隐藏期间**不会丢**：订阅常驻，`active=false` 只影响渲染，不影响回调（见 §10 第 15 条）。
- 视图是只读的：除「用户主动清红点」外，界面不要反向写计数。

显示规则（按 `_maxCount` 参数化，默认 99）：

| 条件 | `Visual` 显隐 | 数字 |
| --- | --- | --- |
| ID 为空 | 隐藏 | 无 |
| 未注册或计数为 0 | 隐藏 | 无 |
| 1 ~ `_maxCount` | 显示 | 原数字 |
| `> _maxCount` | 显示 | `${_maxCount}+` |
| `_dotOnly = true` | 显示 | 隐藏数字，只留圆点 |

`_countLabel` 为空时自动退化为只显示圆点；`_maxCount` 非法（非有限或 `< 1`）按 99 处理。

## 6. 数据流与时序

```
业务模块 ──Register(id, parent)──▶ 注册树
业务数据 ──Set/Add/Clear──────────▶ 计数
                                      │
                                      ▼
                              脏 ID 事件（含祖先）
                                      │
                                      ▼
                            RedDotBadge ──▶ Visual 的 active / Label
```

启动顺序（括号内是现有工程里的落点，方便对照）：

1. `AppEntry.start`：`SettingsService.Initialize()`（`AppEntry.ts:31`）→ `RedDot.Initialize()` → `registerAppRedDots()`（+ DEV 演示种子）→ `UIRuntimeRegistry` / `UIManager.init()`（`AppEntry.ts:35-53`）。`Initialize` / `Dispose` 必须幂等、不抛异常。
2. 业务数据初始化：从存档/配置算出各 ID 计数，用 `RedDot.Batch` 一次性写入。
3. 主界面打开分两拍：
   - **Create 阶段**：窗口挂到层级，子节点 `onLoad` 订阅、`onEnable` 按当前计数显隐（此时窗口的 `initEvent` / `onOpen` 还没执行）；
   - **Open 阶段**：`resetBindings → initEvent → onOpen → 打开动画`。
   不要假设「`onOpen` 里的 `Set` 一定被已订阅的视图收到」——`onLoad` 与 `onOpen` 的先后取决于引擎激活时机；`onEnable`/`onLoad` 的快照会兜底，但设计上不应依赖这个顺序。
4. 游戏数据变化：业务调用 `Set/Add`，父节点自动更新，相关红点刷新。
5. 用户进入页面或领取：业务调用 `Clear/ClearTree`，父入口红点同步减少。
6. 动态列表项移除：`Unregister(id)`，父节点重算，红点隐藏。
7. `AppEntry.onDestroy`：先 `UIManager.dispose()`，再 `RedDot.Dispose()`。`UIManager.dispose()` 不销毁界面节点（由场景卸载负责），所以 badge 的退订可能晚于 `Dispose`，退订必须对已清空的 dispatcher 安全。

建议在打开主界面前完成注册和计数初始化，避免“先空后亮”的闪烁；如果数据确实晚到，批量写入也能保证只刷新一次。

### 6.1 树负责算，事件负责通知

不要让孩子节点逐级向父节点冒泡事件。红点树只是“聚合计算图”，通知走一条独立的事件通道：

- 写入时，Store 沿 parent 链向上重算 `total`；`ClearTree` / `ResetCounts` 先自底向上重算整棵子树，再沿父链向上。
- 脏集按统一规则收集（见 §5.1）：`total` 发生变化的节点（含当前节点与全部祖先）、新注册节点、被移除节点及其全部子孙。
- 最后只发一次事件：`{ ids: dirty }`（batch 内合并；batch 为空或脏集为空时都不广播）。
- 视图收到事件后，用自己的 ID 做 `change.ids.has(id)` 过滤，再 `Get(id)` 取最新值刷新。
- 每次广播的 `ids` 是新的 `Set` 快照，监听器之间不会互相污染。

所以父级不是“收到子级事件”，而是“自己的 `total` 被重算后进入了脏集合”。兄弟节点不会收到通知，因为它们的 `total` 没变。

一次 `Set('main/stage/1001', 100)` 的实际过程（前态：`1001=0`、`1002=20`、`team=2`，即 §3.4 示例树去掉 1001 的 100）：

```
重算：1001.total=100 → stage.total=120 → main.total=122
脏集：{ 1001, stage, main }
事件：emit({ ids: {1001, stage, main} })
刷新：三个 ID 上的红点各读一次 Get()
```

一次 `ClearTree('main/stage')`（前态同 §3.4：stage=120、1001=100、1002=20）：

```
清零并自底向上重算：1001.total=0、1002.total=0 → stage.total=0
再沿父链：main.total = team 2 + stage 0 = 2
脏集：{ 1001, 1002, stage, main }（每个节点都是因为 total 真的变了）
事件：emit 一次
```

一次 `Unregister('main/stage/1001')`：

```
移除：1001
重算：stage、main
脏集：{ 1001, stage, main }
事件：emit 一次
```

一次 `Set` 写入相同值：

```
total 没变，且没有结构变化 → 脏集为空 → 不广播
```

一次 batch 内净变化为 0（例如 `Set(a,1)` 再 `Set(b,4)`，而 a/b 同属 main、main 总数前后都是 5）：

```
若实现以 batch 起点为基线、flush 时复核：脏集 { a, b }，main 被剔除 → 不刷新 main
若实现只按单次写入比较：脏集 { a, b, main } → main 多刷新一次（无害）
两种实现都可以，但文档只承诺「单次写入 total 不变不广播」，不要承诺 batch 内一定剔除净零变化。
```

一次 batch 内「自身 2 变 1、子节点补 1」（总数不变）：

```
只按单次写入比较 → main 在第一次写入时进脏集，flush 时仍可能被广播（多一次无害刷新）
以 batch 起点为基线复核 → 可以剔除 main，不刷新
两种实现都可以；文档只承诺单次写入的判定，batch 的净零抑制是可选项。
```

### 6.2 为什么不逐级冒泡

| 方案 | 问题 |
| --- | --- |
| 子节点向父节点冒泡 | 每层一次回调，N 层就 N 次；父节点还要重复重算；视图必须和树节点强绑定 |
| 父节点订阅所有子节点 | 动态注册/注销时要反复接线，漏一个就永远不更新 |
| 每帧轮询 | 无变化也在跑，而且有延迟 |
| 全局脏 ID 事件 | 一次广播、批量合并、视图与树解耦；当前量级足够 |

补充：

- 事件载荷只带 ID，不带计数。批量写入时同一个 ID 可能变多次，只有最终值有意义；视图通过 O(1) 的 `Get(id)` 读最终状态，不会拿到过期计数。
- 每次广播传一份新的 `Set` 快照；监听器不得拿到会被下一轮复用的可变集合。
- 监听器原则上只读。允许监听器里再写红点，但新脏 ID 进入下一轮，当前一轮发完后再发，**每轮最多广播一次**，禁止同步递归广播；监听器异常用 `try/finally` 隔离并保证 `_emitting` 复位；同一监听器连续触发 3 轮以上记 `Log.error`（见 §5.1）。
- 脏集合用 `Set`，`has` 是 O(1)；视图数量少时，一次全局广播的成本可以忽略。
- 规模变大（上千个列表红点）时，升级为“每个 ID 一组监听器”或“列表控制器统一订阅、按脏 ID 局部刷新”，树的聚合逻辑不变。

## 7. UI 结构与 Cocos 设置

推荐节点结构（**组件节点常驻，显隐只切 `Visual`**）：

```
TeamButton (Button, UITransform)
└─ RedDot (RedDotBadge, UITransform, Widget)   ← 脚本挂这里，永远 active
   └─ Visual (Sprite, UITransform)             ← 可见性只切它，默认 active
      └─ Count (Label)                         ← _countLabel
```

设置建议：

- `RedDot` 节点：只挂 `RedDotBadge`，不挂渲染组件；`UITransform` 约 `40 × 28`；`Widget` 对齐父节点右上（需要显式勾 `isAlignTop` / `isAlignRight`），`top = -4`、`right = -4`，让角标略微压出按钮边缘。
- `Widget.AlignMode`：角标一律用 `ALWAYS`（与仓库现有 Widget 一致，每帧重算的成本可以忽略；`ON_WINDOW_RESIZE` 不跟随父按钮的 Layout/动画尺寸变化，只在 Canvas 级全屏节点上才合适）。
- `Visual`：`Sprite` 作为红色底，`UITransform` 约 `40 × 28`，与 `RedDot` 同尺寸居中；隐藏只切它的 `active`。
- `Count` 标签：字号约 20，白色，固定宽度；加 `LabelOutline`（深红或黑色，2px）提高可读性。`Label.Overflow` 建议先用 `SHRINK` 并**在真机上验证 `99+` 的可读性**——仓库现有 Label 全是 `CLAMP` / `RESIZE_HEIGHT`，没有 `SHRINK` 先例；若效果糊，改为「`RESIZE_HEIGHT` + 足够宽的底图」或缩短上限文本。
- 圆点模式：把 `_dotOnly` 勾上，隐藏 `Count`，把 `Visual` 底图做成约 `24 × 24` 的圆形；或者单独做一个只含圆点的 prefab 变体。
- 层级：`RedDot` 放在按钮子节点的**最后**，保证画在图标上方；它必须是按钮的**直接子节点**，不要放进 `IconViewport`、`ScrollView` 等带 `cc.Mask` 的容器（MainWin 的 `SettingButton` 下就有一个带 Mask 的 `IconViewport`，放进去会被裁掉）。
- 交互：角标上不要加 `Button`、`BlockInputEvents`，也不要挂触摸监听；它只是显示层，不能挡住父按钮点击。
- 节点默认激活：`RedDot` 组件节点在 prefab 里必须默认 `active = true`（`onLoad` 只执行一次，初始 `inactive` 会导致订阅不执行）；**运行时不要隐藏组件节点**，隐藏只切 `Visual`。

## 9. 持久化方案

本阶段不持久化红点树。理由：

- 红点计数应该由游戏数据推导。把 `{ "main/team": 2 }` 写进存档，内容更新或数据回滚后会留下“幽灵红点”。
- 注册树是运行时结构，每次启动都要重新注册；它本来就不该进存档。

如果后续要做“跨启动保留未读红点”，只保存业务侧的“已读标记”，启动时重算：

- 新角色：保存已读的角色 id 集合，未读数 = 已拥有角色数 − 已读角色数。
- 新公告：保存最后已读公告 id 或时间戳，未读数 = 更新的公告数。
- 可领取奖励：不保存，直接由奖励数据算。

不建议做一个通用的 `seenCount` 表来覆盖所有场景，因为“数量减少”“内容替换”“id 复用”都会让差值算错。等具体系统出现时，在各自的数据层加字段，再调用 `RedDot.Set` 即可。

如果一定要有通用存储，最低要求是：

- 单独 key，例如 `crashfever.reddot.seen`，带 `v` 版本号。
- 只存已读标记，不存聚合值。
- 解析失败按空处理（红点重新出现，属于安全失败）。
- 存档导入后先 `RedDot.ResetCounts()`，再按导入数据重算。`ResetCounts` 会自底向上重算并只发一次事件，已存在的视图会被正确清零（定义见 §5.1），不要自己逐个 `Clear`。

导入接线的落点（v3 补充）：跨平台存档导入尚未实现，后续接入时在「确认导入 → 覆盖数据」之后、重新打开界面前调用 `ResetCounts()`，然后按导入后的游戏数据重新 `Batch` 写入。重开流程（返回标题再进主界面）不需要 `ResetCounts`，但重复调用 `Initialize` 必须是幂等 no-op。

## 10. 边界与常见坑

1. 父节点未注册：`Register` 直接失败。注册顺序必须先父后子，批量注册按数组顺序处理。
2. 对未注册 ID 调 `Set/Add`：记错误并忽略。动态列表项必须先 `Register` 再 `Set`。未注册 ID 的 `Get/GetOwn` 返回 0、`Has` 返回 false（契约表见 §5.1）。
3. 重复 ID：同父幂等（`initialCount` 被忽略并记 `Log.warn`），异父报错并保留第一次的关系。
4. 动态列表项只 `Clear` 不 `Unregister`：注册表会持续增长，必须在数据项移除时注销；列表全量重建要先清旧 ID。
5. 把 `Unregister` 当成清红点用：会连同子节点一起从树里删掉；只是清计数请用 `Clear/ClearTree`。
6. 红点组件节点初始 `inactive`：`onLoad` 不执行，组件不会订阅，后面也不会自己出现。prefab 里必须默认激活，运行时也不要隐藏组件节点（只切 `Visual`）。
7. 在 `onDisable` 里退订：组件自己隐藏后收不到事件，红点永远无法重新出现。本组件的退订只在 `onDestroy`；也**不要**在 `onEnable` 里重复订阅（`BindingScope.add` 不去重）。
8. 启动时多次 `Set` 要用 `Batch`，否则会连续刷新多个界面。
9. 静态数据会跨场景保留：重开流程、导入存档时用 `ResetCounts/Dispose`；`Initialize` 幂等。
10. 角标不能拦截点击；加完节点后在真机/浏览器上验证按钮边缘仍可点击。
11. `99+` 会撑宽角标：标签固定宽度 + `SHRINK`，底图预留三字符宽度；`SHRINK` 在仓库无先例，必须真机验证可读性，效果差就改 `RESIZE_HEIGHT` + 更宽底图。
12. 父节点显示封顶、存储不封顶；不要把 `99` 写回 Store。
13. 多个红点绑定同一 ID 是允许的，会一起刷新；但不要因此重复写业务数据。
14. 列表里红点很多时，事件回调数等于红点数。当前量级没问题；上千项时改成“列表控制器统一订阅 + 按脏 ID 局部刷新”。
15. **隐藏期间的事件不会丢（v3 修正）**：订阅在 `onLoad`、退订只在 `onDestroy`，`hideBelow` 与缓存关闭都只影响节点是否挂在激活层级上，不碰订阅，事件照常送达。`onEnable` 只在节点本身被激活时触发，**不能作为自隐藏节点的恢复路径**；恢复靠保留的订阅。禁止为了“防丢事件”在 `onEnable` 里重新订阅。
16. 数据初始化晚于界面打开会产生一次闪烁；能提前就提前，不能提前就接受一次批量刷新。不要把「`onOpen` 里的 `Set` 一定被已订阅的视图收到」当设计前提。
17. 角标是只读视图；除“用户主动清红点”外，界面不要反向写计数。
18. 动态 ID 里如果包含用户输入或配置原文，先做字符过滤，避免出现不可见字符、前后空格导致注册和查询对不上（判据见 §5.1）。
19. 视图上的 `redDotId` 拼错不会报错，只会一直隐藏；统一用 `AppRedDotId` 常量，开发期可在组件里用 `IsRegistered` 做一次警告。
20. 同一棵树的红点必须同语义（未读 / 可领取）；跨语义入口不要挂在同一父节点下，否则父入口的 `99+` 是两种语义的混合值，用户看不懂数字为什么不减少（见 §3.3）。
21. `batch` 里抛异常不会自动恢复：实现必须 `try/finally` 回退深度并决定 flush 语义（见 §5.1）；业务侧也尽量避免在 batch 里抛异常。
22. `Dispose` 之后不要继续订阅；`Dispose` 后到达的退订必须是无害 no-op（框架 `UIManager.dispose()` 不销毁界面节点，badge 退订可能发生在 `Dispose` 之后）。
23. `MainWin.prefab` 是 `build-app-ui.py` 的生成物：手工加红点节点前先确认生成脚本是否要同步；重跑脚本会覆盖手改。
24. 红点必须直挂按钮子节点：不要放进带 `cc.Mask` 的容器（如 `SettingButton/IconViewport`），否则角标会被裁剪。
25. 纯色占位底图不可直接染色：`solidBlue.png` 是蓝色，`Sprite._color` 乘算后染红会变暗紫；先补一张纯白圆角图（见 §12）。

# 模块边界

日期：2026-10-30。状态：当前工作约定，随阶段任务调整；不是对原作技术架构的冻结声明。

依据：[项目总纲](项目总纲.md)只确认需求范围，不预先锁定架构。本文记录当前工程如何分目录、依赖方向和测试边界，避免第二阶段的角色与编队继续堆进 `Model/App`。新增或调整模块时先改本文，再拆任务。

## 1. 总原则

- `Model` 是业务层，不是一个类或一个 `AppModel`；`App` 只是应用壳模块。
- `Frame` 只放可复用、与具体玩法无关的通用能力，不依赖 `Model`。
- `Model/App` 只负责启动、标题、主界面、设置、通用确认弹窗和入口流程。
- 角色、编队、关卡、战斗分别建立独立模块，数据和界面都放在自己的目录。
- 不预先建立通用路由框架、通用任务调度器或万能门面；需要时再抽。
- 现有 `Model/App` 文件不为了“看起来整齐”大规模搬家；新代码按本文落位，旧代码在对应任务中逐步迁移。

## 3. 模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `Frame/Base` | 模型/控制器基类的生命周期、模型绑定和模型事件总线转发 | 任何具体角色、编队、战斗业务 |
| `Frame/UI` | 界面注册、分层、生命周期、遮罩、缓存、绑定清理 | 任何角色、编队、战斗业务 |
| `Frame/RedDot` | 红点树、计数、角标组件 | 具体业务红点来源和已读规则 |
| `Frame/Log`、`Frame/Audio` | 日志总线、音频服务 | 业务存档和页面流程 |
| `Model/ModelFactory` | 启动时统一创建并初始化业务模型 | 具体业务流程和界面 |
| `Model/App` | 启动、加载、标题、主界面、设置、确认弹窗、入口恢复检查 | 编队数据、角色配置、关卡、战斗 |
| `Model/Character` | 角色配置结构、配置加载、角色目录查询、选择/详情界面 | 编队槽位和存档、战斗数值执行 |
| `Model/Team` | 30 套编队、4 槽位、队名、当前编队、编队存档、编队界面 | 角色属性/技能、关卡、战斗 |
| `Model/Stage` | 关卡配置、筛选、出战准备 | 战斗执行、编队内部编辑 |
| `Model/Battle` | 战斗、结算、暂停、战斗恢复快照 | 应用启动和标题导航 |
| `Utils` | 单例等无业务工具 | 任何 `Model`、`Frame` 业务 |

`Model/App/Recovery` 目前只服务“标题进入前检查”。正式战斗快照出现后，恢复数据模型归 `Model/Battle`；入口仍由 `App` 调用，不要把两者混成一个模块。

## 4. 依赖方向

允许：

```text
Frame        ←  Model/*
App          →  ModelFactory / Character / Team / Stage / Battle 的服务与界面注册
ModelFactory →  Character / Team / Stage / Battle 的模型
Team         →  CharacterController 的查询接口
Stage        →  TeamController / CharacterController 的接口
Battle       →  CharacterController / TeamController / Stage 的只读接口
```

禁止：

- `Frame` import `Model` 或 `Utils` 中的业务代码。
- `Character`、`Team`、`Stage`、`Battle` import `AppEntry` 或 `Model/App/UI`。
- 功能模块之间直接 import 对方 UI 组件；需要导航时通过 `UIManager` 的字符串 id 或模块入口方法。
- 编队存档复用 `SettingsService` 或 `crashfever.settings`。
- 数据文件 import `cc`；引擎访问放到 Loader、Storage 适配器或 UI 层。

跨模块数据只走服务或控制器接口，不读对方内部状态。例如 `TeamController` 需要角色存在性/显示信息时，依赖 `CharacterController` 的查询接口，不直接读角色配置数组。

## 5. 界面归属与注册

每个界面必须有一个 `ownerModId`，与所属模块一致：

| ownerModId | 界面 |
| --- | --- |
| `app` | BootLoadingWin、TitleWin、MainWin、SettingDlg、ConfirmDlg |
| `character` | CharacterSelectDlg、CharacterDetailDlg |
| `team` | TeamWin |
| `stage` | 后续 StageWin、DeployWin |
| `battle` | 后续 BattleWin、ResultWin |

模块自己提供注册函数，`AppEntry` 只做组合：

```ts
// Model/Team/TeamUiRegistration.ts
export function registerTeamUi(registry: UIRuntimeRegistry): void {
    registry.registerRange([
        UIRegistration.window('team', 'TeamWin', 'ui/team'),
    ]);
}
```

```ts
// AppEntry 组装
registry.registerRange([
    UIRegistration.window('app', 'BootLoadingWin', 'ui/app'),
    // ...
]);
registerCharacterUi(registry);
registerTeamUi(registry);

manager.init({
    // ...
    knownOwnerModIds: ['app', 'character', 'team'],
});
```

当前没有门面需求，不要求马上实现 `IUiFacadeProvider`。界面可以直接使用模块服务；真正出现跨模块门面、批量关闭或权限边界时再补。`ownerModId` 现在至少用于归属校验、按模块关闭和后续扩展。

## 6. 数据、存档与可测试性

每个业务模块按“数据 / 存储 / 控制器 / 引擎适配 / 界面”拆分：

```text
CharacterConfig.ts       纯类型、默认值、校验和加载器接口，不依赖 cc
CharacterConfigLoader.ts resources.load 与 JsonAsset 适配
CharacterModel.ts        角色目录和模型事件，不依赖 cc
CharacterController.ts   配置加载与角色目录查询；不持有数据，不依赖 cc

TeamData.ts              纯类型、默认值、校验，不依赖 cc
TeamSaveService.ts       版本、JSON 校验、主备键读写；注入键值存储，不依赖 cc
TeamModel.ts             编队数据、保存快照和模型事件，不依赖 cc
TeamController.ts        编队操作和存档流程；不持有数据，不依赖 cc
TeamStorage.ts           sys.localStorage 适配，唯一需要 cc 的存储文件
TeamWin.ts               界面生命周期和交互，调用 TeamController
```

这样纯数据和规则可以在 Node 中测试，不需要 Cocos；只有 Loader、Storage 和 UI 需要引擎或桩。

存档约定：

- 每个模块使用自己的键，例如编队 `crashfever.teams` / `crashfever.teams.backup`。
- 存档带版本号；读取只接受当前支持版本，损坏或高版本回退默认值并记录日志，不静默覆盖。
- 编辑期间只改内存；退出编队界面或进入战斗时显式保存。保存失败保留内存修改并返回失败，不能假装成功。
- 取消/关闭界面调用 `Discard()` 丢弃未保存修改，不自动落盘。

## 7. 测试与验收

- 纯数据/规则测试放 `tools/<module>test/`，使用内存存储与固定配置。
- UI 行为测试复用 `tools/uitest/` 的 `cc` 桩，不打开编辑器。
- 每个模块至少覆盖：默认值、边界索引、重复/空值、存档往返、损坏存档、版本不兼容、保存失败。
- 编队模块的测试不能依赖真实 `SettingsService` 或音频服务。
- 测试代码由助手维护；实现与测试冲突时先核对任务书和本文，不要为了变绿改测试。

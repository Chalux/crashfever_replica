## 0. 总体结论

**设计方向可行，但不是一份可以直接照着实现的规格稿。** 三个核心决策（运行时显式注册树、脏 ID 事件、组件自显隐）与仓库现有 `Frame/UI`、`Frame/Event` 的能力吻合，示例数据也基本自洽；问题集中在三类：

1. **规格没定义**：`batch` 抛异常、`resetCounts`、`add`/`initialCount` 的入参归一、未注册 ID 的返回值、门面 `Initialize/Dispose` 语义等，实现者只能自己猜，猜错就是静默失效。
2. **文档自相矛盾**：最典型的是 §10-15「界面隐藏期间的事件会丢」与 §5.4 自己「onLoad 订阅、只在 onDestroy 退订」相反；「total 没变不发事件」与「register/unregister 也要进脏集」也会给出相反的事件次数。
3. **示例与真实工程不符**：§8 的 MainWin 示例缺 import、与现存 `onOpen`/`_onTeamEditBtnPress` 冲突，种子数据放 `onOpen` 会被 30s 缓存重开重播；§5.4 的组件代码会踩「首次激活前被隐藏 → `onLoad` 不执行」的坑。

## 1. 阻断

### B1｜`ClearTree` / `ResetCounts` 没有规定「自底向上重算整棵子树的 total」

- **位置**：§5.1 L212-215（实现要点）、§6.1 L408-415（ClearTree 示例）；对照 §3.5 L108、§6.1 L391-394
- **问题**：§5.1 写「内部维护 `nodes`、`children`、`total` 三张表；写入后**沿父链向上**重算」，§6.1 的 ClearTree 示例写的是「清零：stage、1001、1002；**重算：main.total**」。两句话合起来只能推出「清空子孙的 own、只重算 main」，而 `stage.total`/`1001.total`/`1002.total` 三份缓存没有重算 —— 可是 `get(id)` 读的正是这张 `total` 表。结果：**事件发了、脏集看着对，视图 `Get()` 读到旧值，红点不消失。**
- **证据（已实际运行）**：按 §6.1 字面步骤实现后，`clearTree('main/stage')` 得到 `1001=100, 1002=20, stage=120, main=122`（期望 `0/0/0/2`）；把每个节点当成一次写入、`batch` 合并（即自底向上重算）则得到期望值，且脏集与文档示例完全一致。见 [docs/review/probe/probe-reddot.mjs](review/probe/probe-reddot.mjs) F1。
- **修复**：在 §5.1 L212 后补硬约束：

  > `clearTree` / `resetCounts` 必须**自底向上重算被清零子树的每一个节点的 `total`**（可逐个节点按写入处理，也可一次后序遍历），再沿父链向上重算祖先；不允许只重算祖先。脏集必须包含所有 `total` 因此变化的子孙。

  同时把 §6.1 L408-415 的示例改成「清零：1001、1002、stage（自底向上逐个重算）→ 重算 stage.total=0 → main.total=2」，并在 §11 单测清单加一条「`ClearTree` 后每个子孙 `Get()===0`」。

### B2｜`RedDotBadge` 在「首次激活前」被 setter 隐藏，`onLoad` 永不执行 → 订阅永久丢失

- **位置**：§5.4 L293-297（setter 立刻 `_refresh`）、L299-306（订阅放 `onLoad`）、L337-339（`_setVisible` 直接写 `node.active`）、L347（只把「prefab 默认 active」当唯一前提）；配合 §3.6 L119、§8 L526-527
- **问题**：文档推荐的动态列表顺序是「数据项创建 → `Register`（可带初始计数）→ 设置组件 `redDotId`」，§8 写「列表项实例化后 `badge.redDotId = id`」。而 `redDotId` 的 setter 会立即 `_refresh()`；若此刻计数为 0（红点的常态起点），`_setVisible(false)` 会把节点 `active` 置 false。之后再把列表项挂到激活节点上时，因为节点自身 `active === false`，**`onLoad` 不会执行 → 订阅从未登记**；之后计数从 0 变正数没有任何监听者，红点**永久不出现且无任何报错**。这正是文档自己在 L347/L562 承认的机制，只是没意识到自己的 setter 会触发它。文档还漏了一条关键不变量：「首次挂树前没有任何代码把 badge 自身 `active` 置 false」。
- **证据**：`UICreateStateHandler.ts:23-25`（先 `addToNode` 挂树才触发组件激活，`instantiate` 不触发 onLoad）；`BaseCmp.ts:10-15`（项目已明确认识到「订阅不能挂只触发一次的钩子」）；项目内「普通 Component + 私有 binder」的标准写法是 `FitScaleBox.ts:143-164`（`onEnable` 先 `unbindAll()` 再订阅、`onDisable` 退订、`onDestroy` 兜底）。
- **修复（推荐 A，文档 L348 已经提过但只写了一句话）**：
  - **A. 常驻节点 + `Visual` 子节点**：`RedDotBadge` 挂在**始终 active** 的宿主节点上，显隐只切 `_visual.active`，组件节点本身永不被隐藏。B2 与「在 `onEnable` 里改自身 `active`」（M9）一并消失。请把 L348 的一句话补成可直接照抄的骨架，并把它升级为主方案。
  - **B. 保留单节点方案**：给 `_setVisible` 加 `_loaded` 守卫（`onLoad` 之前只记录目标状态、不改 `node.active`），在 `onLoad` 末尾补一次 `_refresh()`；§8 明确「列表项必须**先挂树、后设 `redDotId`**」。
  - 无论 A/B，§11 任务 3 都要加一条验收：「列表项初始 0 → 后变 2，红点能出现」。

### B3｜§10-15「界面隐藏期间的事件会丢」与 §5.4 的订阅常驻设计相反

- **位置**：§10 第 15 条 L571、坑 7 L563；对照 §5.4 L299-315、L345-346
- **问题**：badge 的订阅在 `onLoad`、退订只在 `onDestroy`（节点隐藏只触发 `onDisable`，组件和订阅都还在），所以**隐藏期间事件不会丢**；隐藏状态下收到事件还会把 `node.active` 重新置 true（L337-339）。L345-346 自己也说「一旦退订就再也收不到事件，红点永远无法重新出现」—— 如果隐藏期间事件真的会丢，这套自显隐机制根本不可能工作。按坑 15 的字面意思去补一层「`onEnable` 里重订阅」的兜底，反而会造成 `BindingScope` 重复登记、回调翻倍，直接违反 §1 的第 4 条目标。
- **证据**：`UIRuntimeData.ts:116-134`（`hideBelow` 只改 `ui.node.active`，不碰订阅）；`BaseCmp.ts:43-48`（「隐藏期间收不到事件」的主语是**在 onDisable 退订的 BaseCmp**，文档把结论外推到了 badge 上）；探针实测「节点 inactive 时 `Set` 仍送达并自动点亮」（`docs/review/probe/probe-reddot.mjs` F8）。
- **修复**：把坑 15 改成按对象区分的两句话：

  > `BaseCmp` 系组件在 `onDisable` 退订，隐藏期间事件会丢，重新激活时由 `initEvent` + 一次快照刷新重建；`RedDotBadge` 的订阅在 `onLoad`→`onDestroy` 区间内始终有效，隐藏/缓存重开期间事件不会丢。但 `onEnable` 只在**节点本身被激活**时触发，**不能作为自隐藏节点的恢复路径**——恢复靠保留的订阅。禁止在 `onEnable` 里补订阅（会翻倍）。

  同时改掉 §5.4 L309 的注释「防止隐藏期间漏掉状态」。

### B4｜门面 `Initialize/Dispose/懒初始化` 三者语义未定义，可能让已订阅的红点永久失聪

- **位置**：§5.2 L254（「`Initialize` 在 `AppEntry.start`……门面内部做懒初始化」）；§11 L611（「重复 `Initialize` 不会留下旧监听」）
- **问题**：`RedDotBadge.OnChanged` 的退订闭包绑定的是订阅那一刻的 `EventDispatcher` 实例。如果「重复 `Initialize` 为了不留旧监听而重建 store/dispatcher」，那么在两次 `Initialize` 之间订阅的 badge 会连着旧 dispatcher 被 `clear()` 掉，此后再也收不到事件（只能等下次 `onEnable`，而自隐藏节点没有 onEnable）。文档既说「懒初始化」（允许在 Initialize 之前就有人订阅），又要求「重复 Initialize 不留旧监听」，两条组合起来就是一个静默失聪陷阱；「`Dispose` 清监听」也有同样问题。
- **证据**：`EventDispatcher.ts:82-84`（`clear()` 直接清表）、`:35-37`（`on` 不返回退订函数）、`:43-50`（`off` 按 handler 身份只删第一个）；`BindingScope.ts:21-24`（登记的是「退订闭包」，闭包捕获旧 dispatcher）。两条验收条款 §11 L611 与 L654（「缓存重开不重复订阅」）在「重建式 Initialize」下互斥。
- **修复**：二选一写死并写进 §5.2/§11：
  - **推荐（dispatcher 身份稳定）**：`EventDispatcher` 作为模块级单例**永不重建**；`Initialize()` 幂等（已初始化时 `Log.warn` 后返回）；`Dispose()` 只 `store.dispose()` + 摘掉门面自己登记的转发监听，**不调用 `dispatcher.clear()`**；懒初始化只保证「store → dispatcher 的转发只挂一次」。
  - 或者：明确「`Initialize` 只允许在 `UIManager.init` 之前调用一次；`Dispose` 之后不得再订阅」，并把 §11 L611 的验收改成「重复 `Initialize` 是 no-op，不产生新监听/不丢旧监听」。
  - 另需补一条：`Dispose` 之后到达的退订调用必须是 no-op（`BindingScope.unbindAll()` 会把异常吞成 `Log.error`，见 S14），并加测试点「`Dispose → Initialize → Set → OnChanged` 仍能收到」。

## 2. 重要

### M1｜`resetCounts()` 没有任何「重算 / 脏集 / 事件」规定

- **位置**：§5.1 L202-203、L210-217；§9 L553（「存档导入后先 `ResetCounts()`，再按导入数据重算」）
- **问题**：`resetCounts` 是唯一一个批量修改整棵树的 API，却只写了「所有计数归零，保留注册树」，没写是否重算全树 `total`（同 B1，且更严重：所有内部节点都会过期）、哪些 ID 进脏集、是否发一次事件、在 `batch` 内如何表现。按字面实现（只把 own 置 0、不重算、不发事件）会得到：`Get()` 仍是旧值、界面不刷新，§9 的导入流程直接失效。探针实测 `resetCounts()` 后 `Get(main)=122`、事件 0 次。
- **修复**：补等价定义：

  > `resetCounts` ≡ 对所有根执行 `clearTree`（自底向上重算），并作为隐式 batch 只发一次事件；脏集为所有 `total` 发生变化的节点；若在 `batch` 内调用则并入当前批次。

  并把「`snapshot()` 中每个节点满足 `total === own + Σ children.total`」写成 §11 的验收不变量（一条断言就能测出 B1/M1 的残留）。

### M2｜`batch(fn)` 没有异常语义：按最自然实现，`fn` 抛异常后事件泵永久静默

- **位置**：§5.1 L193-194、L215；§11 L594/L658
- **问题**：文档只写「合并多次注册/写入，只发一次；支持嵌套；最外层结束时统一发送」。`fn` 抛异常时：是否 flush 已累积的脏 ID？`batchDepth` 是否回退？异常吞掉还是向上抛？全部未定义。按最自然写法（`depth++; fn(); depth--;` 没有 `try/finally`），异常后 `depth` 停在 1，此后**所有红点写入只进 pending、永不 flush**，无日志，直到重启进程。探针实测：异常后 3 次后续写入事件数均为 0。
- **修复**：补一条必须实现的约束：

  > `batch` 必须用 `try/finally` 保证深度回退；`fn` 抛异常时先按最外层规则 flush 已累积脏 ID（或明确丢弃并 `Log.error`），再把异常向上抛。嵌套 batch 逐层回退。

  §11 单测加「batch 内抛异常后，深度归零且后续写入能正常发事件」。

### M3｜`add` / `register(initialCount)` 没有和 `set` 对齐的入参归一规则

- **位置**：§5.1 L165（register）、L172-176（set 有规则、add 没有）
- **问题**：`set` 规定「负数按 0、小数向下取整、NaN/Infinity 按 0」，但同一张 Store 的另外两个写入口没有对应规则：
  - `add(id, NaN)` → `Math.max(0, own + NaN) = NaN` 写进 own 并沿祖先链污染 `total`；`total !== total` 会让「旧值≠新值」永远成立，该节点及祖先此后**每次写入都被判定为变化**，只能靠 `set/clear/resetCounts` 自救；
  - `add(id, 2.5)` 让 `own=2.5`，而 `set(2.5)` 会 floor 成 2 —— 同一个计数两条入口口径不同；
  - `register(id, parent, -5)` 直接把 own 写成负数，**父节点聚合值可为负 → `has()=false` → 入口红点被兄弟节点的真实计数掩盖而消失**（后果最重：用户直接看不到红点）。
- **修复**：定义规格级 `normalizeCount(v)`（非有限→0、负数→0、floor），`set`、`add` 的结果、`register(initialCount)` 统一走它；`add` 的承诺改成「结果恒为 0 以上的整数」；§11「负数与 NaN」验收补 `add(NaN)`、`add(Infinity)`、`register(initialCount=-1)`、`register(initialCount=NaN)`。

### M4｜未注册 ID 的 `Get/GetOwn/Has/Clear/ClearTree` 行为未定义，而视图隐藏逻辑依赖它

- **位置**：§5.1 L168（unregister 未知 ID 静默）、L185-191（get/getOwn/has 无契约）、L217；§5.4 L355（「未注册或计数为 0 → 隐藏」）
- **问题**：注销整棵子树时，视图会收到含「已移除子孙」的事件并执行 `RedDot.Get(id)`，但 `Get(已注销)` 返回什么完全没写。如果实现者返回 `-1` 或抛异常，§5.4 的「注销后视图归零隐藏」就不成立。`clear`/`clearTree` 对未注册 ID 是静默、记 error 还是抛异常也完全没写（`unregister` 明确静默、`Set/Add` 明确记 error，口径三套）。
- **修复**：补一张契约表：

  > 未注册 ID：`get`/`getOwn` 返回 `0`，`has`/`isRegistered` 返回 `false`；`set`/`add` 记 `Log.error` 并忽略；`clear`/`clearTree`/`unregister` 静默忽略。视图可以假定「未注册 ID 的 `Get` 永远安全且返回 0」。

### M5｜脏集规则自相矛盾：「只有 total 真的变了才进脏集」vs「register/unregister 也要进脏集」

- **位置**：§5.1 L213-214；§6.1 L392、L429；§11 L594「总数不变不发事件」
- **问题**：对下面两个真实场景，两条规则给出相反的事件次数结论：① `register(id, parent, 0)`（动态列表最常见的 0 计数注册）—— 没有任何 total 变化，按 L214 应发事件，按 L392/L429 不应发；② `unregister` 一棵计数全为 0 的子树 —— 祖先 total 不变，但被移除节点必须进脏集否则视图不隐藏。文档没裁决，§11 的「事件次数」断言必然打架。
- **修复**：把规则改成可判定的并集：

  > 脏集 = `{ total 发生变化的节点 }` ∪ `{ 新注册节点 }` ∪ `{ 被移除节点及其全部子孙 }`；事件仅在脏集非空时发送（batch 内合并）。§11 的「总数不变不发事件」改写为「**无注册/注销时**，只有 total 变化才发事件」。

  附带：如果要真正兑现 §5.1 L213「避免总数不变的无效刷新」，batch 必须**以 batch 起点为基线、在 flush 时复核并剔除净未变节点**；做不到就删掉这个承诺，只保证「单次写入不广播」。

### M6｜聚合公式把不同语义的数量相加，正是 §3.3 自己禁止的事

- **位置**：§3.3 L76-84 vs §3.4 L85-101、§8 L511-517
- **问题**：§3.3 明确「同一个红点只能选一种语义，把『未读』和『可领取』加在同一个数字里会导致用户看不懂为什么数字不减少」，但 §3.4 的 `total = own + Σ children` 对整棵树无条件求和。§8 的例子就是「编队（可领取）2 + 关卡（未读）120 = main 122」，父入口显示的正是混合值。文档没有任何树级约束阻止这种写法（既没有「同一棵树必须同语义」，也没有「父节点 own 必须为 0」）。
- **修复**：补一条树级约束并让示例遵守：同一棵树的红点必须同语义；父节点 `total` 只汇总同语义子项；不同语义的入口不要挂在同一父节点下（或父节点只显示圆点：任意子项 >0 即亮）。

### M7｜单测工程与现有 UI 冒烟工程会互相打断，文档未定义编译单元

## 5. 需实测清单（静态代码无法判定，建议在文档里标注）

1. 首次挂树时 `onLoad/onEnable` 是同步还是延迟触发（决定「onLoad 订阅」与「onOpen 里 Set」的先后）。
2. 在 `onEnable` 内把自身 `node.active` 置 false 的回调顺序、是否重复触发 onDisable/onEnable、是否有引擎告警。

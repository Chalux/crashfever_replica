## 2. 阻断级发现

### F1【严重度：阻断】§5.1「写入后沿父链向上重算」与 §6.1 的 ClearTree 步骤对子树不成立：按字面实现子树 `total` 残留、Get 不归零（规格缺口）

**文档位置**：§5.1 L212-213（实现要点）、§6.1 L408-415（ClearTree 示例）；对照 §6.1 L391-394、§3.5 L108

**问题**

§5.1 L212-213 规定：

> 内部维护 `nodes`、`children`、`total` 三张表；写入后沿父链向上重算……
> 写入前记录受影响节点（当前节点 + 祖先）的旧聚合值，写入后比较；只有聚合值真的变化才进入脏集合。

而 §6.1 L408-415 的 ClearTree 示例写的是：

```
一次 ClearTree('main/stage')：
清零：stage、1001、1002
重算：main.total
脏集：{ stage, 1001, 1002, main }
事件：emit 一次
```

两处不能同时成立：

1. 按示例字面——「清零子树 own，只重算 `main.total`」——`stage.total`、`1001.total`、`1002.total` 三份**缓存**没有被重算（§5.1 L212 明确 `total` 是一张表，`get(id)` 读它）。`main.total` 又会用「未重算的 `stage.total=120`」去算，结果仍是 122。于是 `ClearTree` 之后 `Get` 仍返回旧值，视图读到旧值、红点继续亮着——「整个模块重置」实际不生效。
2. 按 §5.1 L213「每次写入都做旧值/新值比较」把子树每个节点都当成一次写入（重复 `_recomputeUp`），才能得到示例想要的「全 0 + main=2」；但这时 §6.1 的「重算：main.total」这一行是错/不完整的，且文档从未写明 ClearTree 必须自底向上重算子树 `total`。

也就是说：**§6.1 给出的脏集只有按「逐节点写入 + 自底向上重算」才能得到，而它写出的步骤只重算了一个祖先节点。** 这是规格缺口（正确实现只差一句话），不是设计不可行；但按示例字面落地一定出 bug。

**复现/证据**（探针 §3，实际运行 1 条 FAIL）

初始状态按 §3.4 示例表：`main/team=2`、`main/stage=0`、`1001=100`、`1002=20`（`main` 自身 0，合计 122）。

```
调用序列：clearTree('main/stage')
按 §6.1 字面步骤的实际运行结果：1001=100, 1002=20, stage=120, main=122；emit 1 次；脏集 4 个 ID
文档示例的期望：1001=0, 1002=0, stage=0, main=2；emit 1 次；脏集 4 个 ID
```

事件发了、脏集看着对，但视图 `Get()` 读到的是旧值，红点不消失。

对照实现（同样的初始状态，每个节点当成一次写入 + `batch` 合并，即「自底向上重算」）：

```
调用序列：batch(() => clearTreePerWrite('main/stage'))
实际：1001=0, 1002=0, stage=0, main=2；emit 1 次；
脏集 = {main, main/stage, main/stage/1001, main/stage/1002}（与文档示例一致）
```

对照实现与文档示例的脏集一致，证明缺陷只在「ClearTree 的子树的 `total` 谁来重算」这一点上；修复只需补一句硬约束。

**修复建议**

1. 在 §5.1 实现要点补一句硬约束：
   > `clearTree` / `resetCounts` 必须**自底向上重算整棵子树**的 `total`（可以按字节点的写入逐个重算，也可以一次后序遍历），再沿父链向上重算祖先；不允许只重算祖先。脏集必须包含所有 `total` 因此变化的子孙。
2. 把 §6.1 L408-415 的示例改成：
   ```
   清零：1001、1002、stage（自底向上，逐个重算各自 total）
   重算：stage.total=0 → main.total=2
   脏集：{ 1001, 1002, stage, main }（每个节点进入脏集的原因都是「total 真的变了」）
   emit 一次
   ```
3. §11 L594 的单测清单增加一条：`ClearTree 后 Get(每个子孙)===0`（现在只写了「Clear 与 ClearTree」，没有断言 Get 的值）。

### F2【严重度：阻断】`batch(fn)` 没有异常语义：按最自然实现，fn 抛异常后 `batchDepth` 永久卡住，此后所有事件静默丢失

**文档位置**：§5.1 L193-194（API）、L215（批量实现要点）；§11 L594/L658（验收要求「批量只发一次」）

**问题**

文档只写了：

> `batch(fn: () => void): void` —— 合并多次注册/写入，只发一次变更事件；支持嵌套。
> 批量期间只累积脏 ID，最外层 `batch` 结束时统一发送。

完全没有规定 `fn` 抛异常时：

- 是否要继续 flush 已累积的脏 ID（还是直接清空 `pending`）？
- `batchDepth` 是否必须回退？
- 异常是继续向上抛，还是吞掉记日志（§5.1 L217 只说「非法参数不抛异常」，不涉及 fn 异常）？

按最自然的实现（`depth++; fn(); depth--;`，没有 `try/finally`）：

- 异常从 `batch` 抛出后 `depth` 停在 1；
- 之后**任何**写入都只进 `pending`，永远不再 flush；
- 所有红点从这一刻起不再更新，直到进程重启；
- 再套一层 `batch` 只会让深度变成 2，仍然救不回来。

这是「数据在变、事件永不发」的静默失聪，且不会有任何日志——比抛异常本身更难排查。**修复要求：必须写清 `try/finally` + 异常语义（flush 还是清空 pending）。**

**复现/证据**（探针 §5，实际运行 3 条 FAIL）

```
调用序列：
  batch(() => { set('main/a', 3); throw new Error('boom'); })
实际运行：batchDepth=1（卡住）；events=0；pending={main/a, main} 未 flush
后续：set('main/a', 7); set('main/a', 9) 之后 events 仍为 0，Get('main/a')=9
再套 batch(() => set('main/a', 10))：batchDepth 仍为 1，events 仍为 0
期望（规格应明确）：异常后 batchDepth=0；已写数据至少能通过一次 flush 或后续写入发出事件
```

**修复建议**

在 §5.1 L215 后补一条：

> `batch` 必须用 `try/finally` 保证 `batchDepth` 回退：`fn` 抛异常时，先按最外层规则 flush 已累积的脏 ID（或明确丢弃并 `Log.error`），再把原异常向上抛（二选一并写明；推荐「flush 后向上抛」，避免业务 try/catch 吞掉异常时状态与视图不一致）。

并在 §11 任务 1 的单测里加一条：`batch` 内抛异常后，`batchDepth` 归零且后续写入能正常发事件。

## 3. 重要级发现

### F5【严重度：重要】`resetCounts()` 没有任何脏集/重算/事件规定，按字面实现存档导入后红点不消失

**文档位置**：§5.1 L202-203（API）、L210-217（实现要点）；§9 L553（「存档导入后先 ResetCounts」）；§11 L594

**问题**

`resetCounts` 是唯一一个**批量修改整棵树**、且被 §9 L553 写进「导入存档」流程的 API，但：

- §5.1 实现要点（L210-217）只讲了普通写入、register/unregister、batch，**完全没有提到 resetCounts**；
- API 注释只有一句「所有计数归零，保留注册树」（L203），没有说：
  - 是否要重算全树 `total`（同 F1 的子树问题，`resetCounts` 更严重：所有内部节点的 `total` 都会过期）；
  - 是否要收集脏 ID（理论上所有原 `total>0` 的节点都要刷新）；
  - 是否发一次事件、在 batch 内如何表现。

按字面实现（只把 `own` 置 0，不重算、不发事件）：`Get()` 仍返回旧值、视图不刷新——§9 L553 的「导入存档后先 `ResetCounts`，再按导入数据重算」直接失效，旧红点残留到下一次相关写入。

**复现/证据**（探针 §7，实际运行 3 条 FAIL）

```
初始：§3.4 示例树（main=122, stage=120, 1001=100, 1002=20, team=2）
调用序列：resetCounts()
实际运行：Get 仍为 main=122, stage=120, 1001=100, 1002=20, team=2；snapshot 最大 total=122；events=0
期望（§5.1 L203 + §9 L553）：所有 Get=0，snapshot 的 total 全 0，emit 1 次（含全部原非零节点）
```

**修复建议**

补成等价定义：

> `resetCounts` ≡ 对所有根节点执行 `clearTree`（自底向上重算），并作为一个隐式 batch 只发一次事件；脏集为所有 `total` 发生变化的节点。若 `resetCounts` 在 `batch` 内调用，则并入当前批次。

同时把「`snapshot()` 中每个节点满足 `total === own + Σ children.total`」写成 §11 的验收不变量（可用 `snapshot` 一次性测出 F1/F5 的残留）。

### F6【严重度：重要】`add` / `register(initialCount)` 没有入参归一规则：NaN/Infinity/小数/负数会污染聚合，负 `initialCount` 可掩盖兄弟节点的真实红点

**文档位置**：§5.1 L165（register）、L172-173（set 有规则）、L175-176（add 无规则）

**问题**

文档只给 `set` 写了归一规则：

> `set`：负数按 0，小数向下取整，NaN/Infinity 按 0。

但同一张 Store 里还有两条写入口：

| API | 文档规则 | 后果 |
| --- | --- | --- |
| `add(id, delta)` | 只有「结果不会小于 0」 | `delta` 为 NaN → `Math.max(0, own+NaN)=NaN`，**写进 `own` 并沿祖先链污染所有 `total`**；`own+Infinity`、`Infinity+(-Infinity)` 同样产生 Infinity/NaN；小数 delta 让 `own` 变成 2.5，而 `set(2.5)` 是 2，同一个计数两条入口口径不同 |
| `register(id, parent, initialCount)` | 只有「只在首次注册时生效，默认 0」 | 负数 `initialCount` 直接把 `own` 写成负数，父节点聚合值可为负；`has()`/显示用 `total > 0` 判断，父节点上的真实红点会被**负数子节点抵消而隐藏** |

最坏的不是 NaN 本身（显示层 `formatRedDotCount` 会把 NaN 当 0 隐藏），而是：

1. NaN 进入 `total` 后，`total !== total`，按 §5.1 L213 的「旧值 vs 新值比较」**每次写入都被判定为变化**，该节点及其祖先会永久被广播；`add` 无法自救（NaN 吸收），只能用 `set`/`clear`/`resetCounts` 修；
2. 负数 `initialCount` 会让父节点 `Get` 变成负数 → `has()=false` → 整个入口红点消失，而兄弟节点上明明有待处理数量。这是计数语义里后果最重的一种（用户直接看不到红点）。

**复现/证据**（探针 §8，实际运行 3 条 FAIL）

```
(a) NaN
初始：main{a=5}
add('main/a', NaN)
期望（与 set 对齐）：get(a)=5, get(main)=5, has(main)=true
实际运行：get(a)=NaN, get(main)=NaN, has(main)=false（真实 5 个红点被隐藏）
add('main/a', -1) 之后仍为 NaN（Math.max(0, NaN)=NaN）

(b) Infinity
add('main/a', Infinity)          → get(main)=Infinity（显示 99+，但 Get 返回 Infinity）
再 add('main/a', -Infinity)      → get(main)=NaN（Infinity + -Infinity）

(c) 小数
add('main/a', 2.5)               → get(a)=2.5；而 set('main/a', 2.5) → 2
实际运行：同一条计数，两条入口得到 2.5 和 2，显示层 floor 后都是 2

(d) 负 initialCount（最严重）
register('main', null)；register('main/x', 'main', -5)；register('main/y', 'main', 3)
期望（与 set 的「负数按 0」对齐）：get(main/x)=0, get(main)=3, has(main)=true, 显示 3
实际运行：get(main/x)=-5, get(main)=-2, has(main)=false, 显示隐藏
→ y 上真实存在的 3 个红点被 x 的 -5 抵消
```

**修复建议**

1. 定义一个规格级的 `normalizeCount(value)`：`Number.isFinite` 为 false → 0；`< 0` → 0；`Math.floor`；`set` / `register(initialCount)` / `add` 的结果统一走它（`add` 可以用 `normalizeCount(own + normalizeCount(delta))`，或明确 `delta` 只接受「有限整数，否则拒绝并 `Log.error`」）。
2. 明确 `add` 的语义是「先归一 delta，再加、再 clamp、再 floor」，并保留「结果不会小于 0」的承诺（对 NaN 也成立）。
3. 在 §11 L594 的「负数与 NaN」验收里补上：`add(NaN)`、`add(Infinity)`、`register(initialCount=-1)`、`register(initialCount=NaN)` 四类用例。

### F7【严重度：重要】未注册 ID 的 Get/GetOwn/Has/Clear/ClearTree 行为未定义，而注销归零的规格依赖它们

**文档位置**：§5.1 L168（unregister 未知 ID 静默忽略）、L185-191（get/getOwn/has 无未注册规则）、L217（错误清单）；§5.4 L355（「未注册或计数为 0 → 隐藏」）；§10 L558（Set/Add 未注册记错误）

**问题**

§5.1 L146 说注销时「还包含被移除的子孙」，视图收到这些 ID 后会执行 §5.4 L324 的 `RedDot.Get(id)`，但 `Get` 对「已注销 ID」返回什么完全没写。同理 `getOwn`、`has` 对未注册 ID 的返回值，以及 `clear`/`clearTree` 对未注册 ID 是静默忽略、记错误、还是抛异常（`unregister` 明确静默忽略，`Set/Add` 明确记 error，`Clear/ClearTree` 完全没写——错误日志口径另见 F18）。

这不是文档完整性小事：如果实现者让 `Get(未注册)` 返回 `-1`/抛异常，§5.4 的「注销后视图归零隐藏」就不成立（Badge 收到事件后要么显示错误值，要么异常被 §5.1 L216 吞掉、红点残留）。

**复现/证据**（探针 §9，实际运行 3 条 PASS——PASS 只说明原型按 0 假设，文档本身未规定）

```
register('main')；register('main/a','main',5)；unregister('main/a')
Get('main/a')        → 0（文档未规定；§5.4 L355 的隐藏逻辑需要它）
GetOwn('main/a')     → 0（文档未规定）
Has('main/a')        → false（文档未规定）
Clear('main/a')      → 记 error + 忽略（文档未规定）
ClearTree('main/a')  → 记 error + 忽略（文档未规定）
```

**修复建议**

在 §5.1 API 注释里补全：

> 未注册 ID：`get`/`getOwn` 返回 `0`，`has` 返回 `false`，`isRegistered` 返回 `false`；`set`/`add` 记 `Log.error` 并忽略；`clear`/`clearTree`/`unregister` 静默忽略（`unregister` 保持现状）。视图层可以假定「未注册 ID 的 `Get` 永远安全且返回 0」。

### F8【严重度：重要】§10-15「界面隐藏期间的事件会丢」与本文档 §5.4 的订阅常驻设计相反（重点核查项，明确判断：该条陈述错误）

**文档位置**：§10 第 15 条 L571；§5.4 L299-306（onLoad 订阅）、L308-311（onEnable 补刷新 + 注释）、L313-315（只在 onDestroy 退订）、L345-346（明确否定 onDisable 退订）、L347（硬性要求 prefab 默认 active）

**问题与明确判断**

§10-15 的原文：

> 红点只在数据变化时推送；**界面隐藏期间的事件会丢**，所以重新激活时必须从当前状态重建，不能依赖增量。

**判断：这条陈述在本文档自己的组件规格下是错的。**

理由（全部来自文档自身）：

1. Badge 的订阅发生在 `onLoad`、退订只发生在 `onDestroy`（L299-306、L313-315）；节点 `active=false` **不会**触发 `onDestroy`（隐藏只触发 `onDisable`，组件实例和订阅都还在）。
2. L345-346 还专门解释了为什么不能在 `onDisable` 退订：「一旦退订，就再也收不到『计数变大』的事件，红点永远无法重新出现」——如果隐藏期间事件真的会丢，这段论证反而解释不了组件重新出现。
3. L347 硬性要求 prefab 默认 `active=true`，就是为了保证 `onLoad` 至少执行一次；订阅之后，隐藏只影响渲染，不影响 dispatcher 回调。
4. 组件在事件回调里直接 `node.active = visible`（L337-339），隐藏状态下收到事件时还会把自己重新激活。

**真正会丢事件的只有一种情况**：组件被销毁（`onDestroy` → 退订）之后再变化——但此时组件已不存在，重新创建时会重新 `onLoad` 订阅 + `onEnable` 读当前值（L308-311），所以「重建」结论本身成立，只是**理由错了**。

§5.4 L309 的注释「重新激活时从当前状态补一次，防止隐藏期间漏掉状态」沿用了同一个错误前提，应一并改写。

**复现/证据**（探针 §10，实际运行 2 条 PASS，直接证明事件没丢）

```
初始：main{a=0}；Badge 绑定 a
onLoad() 订阅；onEnable() 刷新（total=0 → active=false）
模拟界面隐藏：node.active=false（未销毁，未退订）
调用：set('main/a', 5)
实际运行：Badge 的监听器仍被调用，_refresh 读到 5，active=true；events=1
若 §10-15 的说法成立：事件丢失，Badge 应保持隐藏
```

**修复建议**

把 §10-15 改写为（同时改 §5.4 L309 的注释）：

> 视图的订阅在 `onLoad` 登记、只在 `onDestroy` 退订，**节点隐藏期间事件不会丢**；但窗口/列表项可能被销毁后重建，因此 `onEnable` 必须从当前 `Get(id)` 重建一次状态，不能依赖「组件存活期间收到的增量」。不要在 `onDisable`/`onEnable` 里反复订阅或退订，否则回调会翻倍或永久失聪。

这条不改，最直接的危害是：实现者会相信「事件会丢」，从而在 `onEnable` 里**重新订阅**（或加一层全局 resync 监听），造成 §1 目标「隐藏再显示时不重复订阅」被破坏、回调翻倍。

### F9【严重度：重要】`_emitting` 只出现在 §6.2 补充里，与 batch、监听器异常、多轮事件次数的交互全部未定义

**文档位置**：§6.2 L443-445；§5.1 L193-194、L215、L216

**问题**

- §5.1 是「实现要点」的权威位置，但那里没有任何 `_emitting` / 监听器内写红点的说明；它只出现在 §6.2 的「补充」里（L444）。
- 与 batch 的两个规则没有对接口径：`batch` 结束「统一发送」（§5.1 L215）时如果正处于 `_emitting`（例如监听器里再开 batch），是**排队到下一轮**还是**递归广播**？文档没写，事件次数由此不确定（1 轮 vs 2 轮）。
- 监听器抛异常（§5.1 L216 说只记日志）时，`_emitting` 是否复位、`nextRound` 是否继续派发，也没写；如果实现漏了 `finally`，同样会永久卡住事件泵——与 F2 是同一类风险。
- 多轮派发的合并策略没写：监听器一次写多个 ID 时，下一轮是「一个事件」还是「每次写入一个事件」？

**复现/证据**（探针 §12，实际运行 2 条 PASS，但语义未规定）

```
监听器 L 在收到含 'main/a' 的事件时执行 batch(() => set('main/b', 2))
调用：set('main/a', 1)
实际运行（按 §6.2「排队」+ §5.1「batch 结束发送」的字面实现）：2 轮事件
  第 1 轮：{main/a, main}
  第 2 轮：{main/b, main}
另一种实现（batch 结束时不看 _emitting，直接递归 _emit）会得到「同步嵌套的 2 轮」
再一种（nextRound 用 Set 合并）可能合成 1 轮：{main/a, main, main/b}
三种都「符合文档」，但事件次数/顺序不同
```

**修复建议**

在 §5.1 实现要点补一条完整规则，例如：

> 监听器只读，但允许写；写入产生的脏 ID 进入 `nextRound`（若正在 `_emitting`）或 `pending`（若在 `batch` 内）。`batch` 的最外层结束与 `_emitting` 结束都走同一个 `flush()`：`flush()` 期间产生的新脏 ID 只进入下一轮，每轮最多广播一次；监听器异常用 `try/finally` 隔离，保证 `_emitting` 一定复位。禁止无限重入：若同一监听器连续触发 3 轮以上，记 `Log.error`（或规定监听器内不得写红点）。

### F10【严重度：重要】聚合公式把不同语义的数量直接相加，正是 §3.3 禁止的「把未读和可领取加在同一个数字里」

**文档位置**：§3.3 L76-83（两种语义不要混用）、§3.4 L85-101（聚合公式与示例）

**问题**

§3.3 L83 明确：

> 同一个红点只能选一种语义。把「未读」和「可领取」加在同一个数字里，会导致用户看不懂为什么数字不减少。

但 §3.4 的聚合公式 `total(id) = own(id) + Σ total(child)` 对**整棵树**无条件求和。§8 的三入口场景里：

- `main/team`（编队）通常是「可领取/待处理」语义；
- `main/stage/<chapter>`（关卡）通常是「未读/新内容」语义；
- 父节点 `main` 的 `total = 2 + 120 = 122` 就是两种语义的直接相加。

§3.4 示例表只给出数字、没有标注每个子树的语义，等于把一个「合法但语义混合」的例子当成标准写法。设计文档没有任何规则阻止这种混用：既没有「同一棵树的子树必须同语义」，也没有「不同语义不得跨树聚合」「父节点 own 必须为 0」之类的约束。

这不一定会在代码层出错，但会让 §3.3 的告诫在树层面失效——用户看到入口上 122，点进去发现「编队里 2 个可领、关卡里 120 个未读」，两个数字的「减少方式」不同，正是 §3.3 描述的用户困惑。

**复现/证据**（文档级推理，无需运行）

```
§3.4 表：main/team own=2 → main/stage own=0, 子项 100+20 → main own=0
main.total = 2 + 120 = 122
若 team 用「可领取」语义、stage 用「未读」语义，则 main 展示的 122 是混合值，
与 §3.3 L83 的明确告诫冲突（§3.3 管的是「同一个红点」，而 main 的显示值正是 total）
```

**修复建议**

在 §3.3 或 §3.4 补一条树级约束，并让 §8 示例遵守：

> 同一棵树（同一根节点下）的路由红点必须使用同一种计数语义；父节点的 `total` 只汇总同语义的子项。若两个入口语义不同（如「可领取」的编队与「未读」的关卡），不要在同一个父节点下聚合，或改为「父节点只显示圆点（有任意子项 >0 即亮），数字只在叶子语义内显示」。

## 4. 建议级发现

> F3/F4 原评为「重要」，按评审主持人意见归入**文档内部不一致**：它们的危害是「文档承诺落空 / 事件次数不可判定」，而不是按文档实现必然产生错误行为。修复成本低，但会直接影响 §11 单测里「事件次数」类断言。

### F3【严重度：建议｜文档内部不一致】「写前记录旧聚合值、写后比较」达不到它自己声明的目标：batch 净变化为 0 时仍会广播

**文档位置**：§5.1 L213；§6.1 L426-430；§11 L594/L658（「总数不变不发事件」）

**问题**

§5.1 L213 声称这样做是为了：

> 避免「自身 2 变 1、子节点补 1」这种总数不变的无效刷新。

但该机制是**逐次写入**比较的：batch 内第一次写入让祖先 `total` 从 5 变 4，祖先就进了脏集；第二次写回 5，脏集只增不减（没有出队规则）。flush 时祖先仍被广播，视图刷新后读到的值与刷新前一样——正是它想避免的无效刷新。

要真正抑制，必须**以 batch 开始时的快照为基线，在 flush 时复核**每个待发 ID 的 `total` 是否与基线相同，相同则剔除；否则应当删除 L213 的承诺，只保证「单次写入」不广播。

**复现/证据**（探针 §4，实际运行 1 条 FAIL）

```
初始：main{a=2, b=3}，main.total=5
调用序列：batch(() => { set('main/a', 1); set('main/b', 4); })
实际运行：脏集 = {main/a, main/b, main}，emit 1 次
期望（§5.1 L213 声明）：脏集 = {main/a, main/b}（main 净变化 0，不应刷新）
```

事件次数是对的（1 次，符合 L215），问题只在脏集多了一个「总数没变」的祖先。**统一改写建议**：要么在实现要点补「batch 开始时做 `total` 快照，flush 时以基线复核并剔除净未变节点」，要么把 L213 降级为「避免单次写入的无效广播」并删掉「自身 2 变 1、子节点补 1」这个在 batch 场景下不成立的例子。

### F4【严重度：建议｜文档内部不一致】register/unregister 的「总是进脏集」与「只有 total 真的变了才进脏集」对同一次操作给出相反结论

**文档位置**：§5.1 L213 vs L214；§5.1 L146（`RedDotChange` 注释）；§6.1 L392、L429；§11 L594

**问题**

- §5.1 L213：「只有聚合值真的变化才进入脏集合」；
- §5.1 L214：「`register` 和 `unregister` **也要**进入脏集合：新节点需要让已存在的视图刷新一次；被移除的节点需要让视图归零隐藏」；
- §6.1 L392：「重算后把 **total 真的变了**的节点收集成脏 ID 集合」；
- §6.1 L429：「total 没变 → 脏集为空 → 不广播」。

对以下两个场景，两条规则结论相反，且都会真实发生（动态列表项就是 0 计数注册/注销）：

1. `register(id, parent, 0)`：没有任何 `total` 变化。**注意：注册一个 `initialCount=0` 的子节点时 `main` 的 `total` 确实没变，所以「事件次数应为 0」是 §6.1 L392/L429 规则推出的结论，不是原型 bug。** 按 L214 应发事件；按 L392/L429 不应发。§11 L594 的验收「总数不变不发事件」会更偏向后者，但 L214 明确要求前者。
2. `unregister` 一棵**所有计数都为 0** 的子树：祖先 `total` 不变。按 L214 应把被移除节点放进脏集（否则视图不隐藏）；按 L392 它们没有「total 变化」，推导不出来。

**复现/证据**（探针 §6，实际运行 1 条 FAIL）

```
调用序列：register('main')；register('main/a', 'main', 0)
实际运行：emit 1 次，脏集 {main/a}（祖先 main 的 total 未变，未进脏集）
同一场景按 §6.1 L392/L429 的判定应为 0 次 —— 文档内部无法判定

调用序列：unregister('main/a')（该子树 total 全为 0）
实际运行：emit 1 次，脏集 {main/a}
同样与 §6.1 L429「total 没变 → 不广播」冲突

反向核对：Unregister('main/stage')（子树有计数）时脏集 = {main, main/stage, 1001, 1002}、emit 1 次，
与 §5.1 L146、§6.1 L417-424 一致 —— 说明「向下收集」本身没问题，缺的是「无 total 变化时怎么算」的裁决。
```

**修复建议（统一改写）**

把脏集规则改成一条可判定的并集：

> 脏集 = `{ total 发生变化的节点 }` ∪ `{ 新注册节点 }` ∪ `{ 被移除节点及其全部子孙 }`；
> 事件仅在脏集非空时发送（batch 内合并）。§11 L594 的「总数不变不发事件」相应改写为「**无注册/注销时**，只有 total 变化才发事件」。

### F11【严重度：建议】示例数据不自洽：1002 未注册、§8「设置」入口未注册、§8 演示值与 §3.4 模型冲突

**文档位置**：§3.4 L93-99；§8 L476-489（注册代码）、L495-502（演示数据）、L511-517（三入口表）

**问题**

1. §3.4 的示例表出现 `main/stage/1002`，但 §3.1 的注册示例（L43-47）和 §8 的 `registerAppRedDots`（L483-489）都没有注册它；按 §8 的动态列表约定它应该是动态注册的关卡节点，但示例没说明。
2. §8 L511-517 的「三个入口」表里列了「设置 0 隐藏」，但 `registerAppRedDots` 只注册了 `main`、`main/team`、`main/stage`，从未注册「设置」入口。按 §5.4 L355「未注册 → 隐藏」，表现碰巧一致，但示例给出的接入方式是不完整的，实现者照抄会得到「设置入口永远隐藏」——包括设置上真有红点时。
3. §8 演示代码 `RedDot.Set(AppRedDotId.stage, 120)` 把 stage 的 **own** 设为 120，与 §3.4 模型（stage own=0，total 由 1001=100 + 1002=20 得到）冲突。如果演示数据与动态关卡同时存在，`main/stage` 的 total 会变成 120+100+20=240（显示仍是 99+，但 §11 L641 验收「父节点计数同步减少」会算出不同的期望值）。

**修复建议**

- 在 §3.4 表下补一句「1002 为动态注册的关卡节点（见 §8 动态列表示例）」；
- §8 的三入口表补上「设置」的注册代码，或删掉该行/注明「演示阶段不注册」；
- 演示数据改成 `Set('main/stage/1001', 100)`、`Set('main/stage/1002', 20)`（与 §3.4 一致），或者明确说明「演示只写 stage 自身，不与动态节点混用」。

### F12【严重度：建议】`formatRedDotCount` 已参数化 `maxCount`，显示规则表却写死 99；非法 `maxCount` 与 `count=0` 的契约未写进文档

**文档位置**：§5.3 L259-263；§5.4 L350-358（显示规则表）、L284-285（`_maxCount` 属性）

**问题**

- §5.4 L352-358 的显示规则表按 `maxCount=99` 写死（「1~99 原数字、≥100 显示 99+」），但组件暴露了 `_maxCount` 属性（L284-285，tooltip「超过该值显示 N+」），`formatRedDotCount` 也接受 `maxCount`。表格应写成「`> _maxCount` 显示 `${_maxCount}+`」，否则读者会以为只有 99。
- `safeMax` 的非法值回退（`maxCount` 非有限或 <1 → 99）只存在于代码里，文档正文没写；`count=0` 返回 `"0"`（而不是空串）也没有契约说明——§5.4 只是碰巧在 `total=0` 时提前 return 才没显示 0。
- 探针核对了 18 组边界（0/负数/NaN/Infinity/浮点/等于上限/非法 maxCount），实现函数本身自洽（§1 段 19 条全部 PASS），问题只是**文档没有把契约写清**。

**复现/证据**（探针 §1，实际运行 19 条 PASS）

```
formatRedDotCount(100, 99)  = "99+"
formatRedDotCount(99, 99)   = "99"     // 等于上限不封顶，与 §5.4 表一致
formatRedDotCount(0)        = "0"      // 返回 "0" 而非空串
formatRedDotCount(5, 0)     = "5"      // maxCount 非法 → 回退 99
formatRedDotCount(100, Infinity) = "99+"  // 同上
```

**修复建议**

显示规则表改成参数化表述；补一段「`maxCount` 非有限或 <1 按 99 处理；`count` 非有限按 0、负数按 0、小数向下取整；`count=0` 返回 `"0"`，调用方负责隐藏」。

### F13【严重度：建议】Store 有 `getOwn`/`snapshot`，门面没暴露；§11 任务 2 的「控制台验证」缺对应入口

**文档位置**：§5.1 L187-188、L199-200 vs §5.2 L221-244；§11 L596-611（任务 2 验收）

**问题**

`RedDotStore` 暴露 `getOwn(id)` 和 `snapshot()`（调试/测试用），但 §5.2 的静态门面只有 `Get/Has/IsRegistered`，没有 `GetOwn/Snapshot`。§11 任务 2 验收要求「控制台可验证 `Register/Set/Get/OnChanged`」，而「验证聚合是否正确」最需要的正是 `getOwn`/`snapshot`。

**修复建议**

门面补 `static GetOwn(id: number)`、`static Snapshot(): readonly RedDotNodeInfo[]`（或明确「调试接口只走 Store，门面不暴露」并说明业务如何取得 Store 实例）。

### F14【严重度：建议】同父重复注册时 `initialCount` 被静默忽略，语义未声明

**文档位置**：§3.1 L61；§5.1 L165（「initialCount 只在首次注册时生效」）

**问题**

「只在首次注册时生效」隐含了同父重复注册时忽略新 `initialCount`，但没说是否记日志/告警。动态列表项如果先 `Register(id, parent, 3)`、后来数据刷新又 `Register(id, parent, 5)`，第二次的数字会**静默丢失**，业务会以为设置成功了。

**修复建议**

明确「同父重复注册 = no-op，忽略 `initialCount` 并记 `Log.warn`」或「同父重复注册时允许更新 `initialCount`（走 set 语义）」。二选一写清楚；同时 §11 补一个对应单测。

### F15【严重度：建议】「非法 ID」没有判据；空串/首尾空格/不可见字符的校验与归一规则缺失

**文档位置**：§5.1 L217（「非法 ID…记 `Log.error` 并拒绝」）；§5.4 L319（空 ID → 隐藏）；§10-18 L574（动态 ID 过滤）

**问题**

L217 把「非法 ID」当成已知概念，但全文没有定义：空串算吗？首尾空格算吗？`id` 不是 string 算吗？§10-18 只给了「先做字符过滤」的建议，§5.4 L319 又把空 ID 当成「隐藏」而不是「注册失败」——实现者无法据此写出确定的行为。

**修复建议**

补一个判据 + 一处归一：

> `isValidId(id) = typeof id === 'string' && id.length > 0 && id === id.trim()`；
> `Register` 与所有写入 API 对非法 ID 记 `Log.error` 并拒绝；不要静默 `trim()`（避免注册与查询对不上）；`Unregister` 保持静默忽略。

### F16【严重度：建议】事件载荷 `ReadonlySet` 的实例所有权未约定，监听器可能相互污染

**文档位置**：§5.1 L145-148

**问题**

`RedDotChange.ids` 是 `ReadonlySet<string>`，但这只是 TypeScript 的编译期约束；运行时如果实现复用同一个可变 `Set`（比如把脏集直接塞进 payload 然后在下一轮 `clear()`），监听器拿到的内容会在下一次广播时被改掉，或监听器自己（用 `any`/JS 侧）修改后影响其它监听器。

**修复建议**

规定「每次广播传入一份新的 `Set` 快照（§6.2 L443 的『只带 ID、一次性载荷』语义），实现不得复用同一个实例」；§11 单测补「监听器收到的 `ids` 在事件结束后内容不变」。

### F17【严重度：建议】§6.1 的 Set 示例依赖未声明的初始状态，不是自洽示例

**文档位置**：§6.1 L399-406

**问题**

示例写：

```
重算：1001.total=100 → stage.total=120 → main.total=122
```

`stage.total=120` 默认了「1002=20 已存在」「team=2 已存在」，但示例本身没写初始状态。读者若从空树开始复现，会得到 100。作为「一次 Set 的实际过程」的示范，应显式给出前态或改成 delta 描述。

**修复建议**

补一行初始状态（引用 §3.4 表），或改成：

```
Set('main/stage/1001', 100)（前态：1001=0, 1002=20, team=2）
delta：1001 +100 → stage +100 → main +100
```

### F18【严重度：建议】对未注册 ID 的错误日志口径三套不一致

**文档位置**：§5.1 L168（unregister 未知 ID 静默忽略）、L217（非法 ID/父不存在/重复冲突记 error）、§3.6 L116（对未注册 ID 调 Set 记错误并忽略）、§10 L558（Set/Add 未注册记错误）

**问题**

同一个「非法操作」在不同 API 上有三种口径：

| API | 文档口径 |
| --- | --- |
| `unregister` 未知 ID | 静默忽略（L168） |
| `set`/`add` 未注册 ID | 记 `Log.error` 并忽略（§3.6 L116、§10 L558、§5.1 L217 的「非法 ID」） |
| `register` 非法 ID/父不存在/重复冲突 | 记 `Log.error` 并拒绝（L217） |
| `clear`/`clearTree` 未注册 ID | **完全未写**（探针 §9 观察到原型只能自己去猜） |

启动阶段一次配置错误可能触发成千上万条 error（动态列表逐个 `Set` 前忘记 `Register`），而 `unregister` 又完全静默——排障时无法从日志区分「预期内的幂等调用」和「真错误」。

**修复建议**

统一写成一张表：每种 API × 每种非法输入的「返回值 / 日志级别（error/warn/静默）」，并说明「幂等调用（重复 register、未知 unregister）应静默或 warn 而不是 error」。§11 补一条「日志口径」单测。

## 5. 建议直接补进文档的规格条款（可粘贴）

> 以下条款按「改动最小、能消除上面全部阻断/重要发现」组织，供设计者取舍。

1. **脏集统一规则（替换 §5.1 L213-214 + §6.1 L392）**
   脏集 = `{ 自身及祖先中 total 发生变化的节点 }` ∪ `{ 新注册节点 }` ∪ `{ 被移除节点及其全部子孙 }`；事件仅在脏集非空时发送（batch 内合并）。batch 内以 batch 起点为基线，flush 时剔除净未变节点（若不做基线复核，就删掉 §5.1 L213 的承诺）。
2. **子树重算（补在 §5.1 L212 后）**
   `clearTree` / `resetCounts` 必须自底向上重算整棵子树的 `total`，再沿父链向上重算祖先；不得只重算祖先。
3. **batch 异常（补在 §5.1 L215 后）**
   `batch` 用 `try/finally` 保证深度回退；`fn` 抛异常时先 flush（或记 `Log.error` 后丢弃）再向上抛；嵌套 batch 的异常同样逐层回退。
4. **resetCounts（补在 §5.1 L203 后）**
   ≡ 对所有根执行 `clearTree` 并作为隐式 batch 只发一次事件；脏集为所有 `total` 变化的节点。
5. **计数归一（补在 §5.1 L165/L176）**
   统一 `normalizeCount(v)`：非有限→0、负数→0、floor；`set`、`add` 结果、`register(initialCount)` 全部使用。
6. **未注册契约（补在 §5.1 L185-191）**
   未注册：`get/getOwn` 返回 0、`has` 返回 false；`set/add` 记 error 忽略；`clear/clearTree/unregister` 静默忽略。
7. **视图订阅（改写 §10-15 L571 与 §5.4 L309 注释）**
   事件在节点隐藏期间不会丢（订阅在 `onLoad`、退订在 `onDestroy`）；`onEnable` 从当前 `Get()` 重建一次状态；禁止重复订阅。
8. **语义约束（补在 §3.3 末尾）**
   同一棵树的红点必须同语义；父节点 `total` 只汇总同语义子项；跨语义入口不得挂到同一父节点下。
9. **可判定的事件次数（补在 §6.2 L444 后）**
   `_emitting` 与 `batch` 共用 `flush()`；每轮最多广播一次；监听器异常用 `try/finally` 隔离，保证 `_emitting` 复位。
10. **错误日志口径（补在 §5.1 L217 后）**
    用一张表列出每种 API × 每种非法输入的返回值与日志级别；幂等调用静默或 warn，配置错误才用 error。
